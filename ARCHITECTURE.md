# Barbets — how it all works

  Barbets is a multi-tenant, play-money prediction market platform for private friend groups. Each group runs its own sealed token economy — no real money ever changes hands. Members create markets ("Will Jake finish the marathon?"), bet tokens on the outcome, and settle up via a parimutuel payout once the group resolves what actually happened. The standout feature is that a market can be *about* someone (`@mentioned` as a "subject"), and that person cannot see the market exists — not in their feed, not in counts, not in notifications — until it resolves.

Live at **https://app.mybarbets.com** (still reachable at `barbets.vercel.app`, Vercel's own alias). Installable as a PWA (Android + iOS) with real web push notifications, and moving toward a native wrapper via Capacitor. `mybarbets.com` is the **separate marketing/landing site**, a different Vercel project built from the `barbets-www` repo — see "Domains and the mybarbets.com split" under Deployment, which is worth reading before touching anything origin-shaped. That's also the domain printed on the shareable reveal ticket (`RevealTicket.tsx`), deliberately rather than the deployment's own URL: that image gets screenshotted and sent to people outside the app, and `mybarbets.com` is the address meant to outlive whatever Vercel deployment happens to be serving it.

**`app/go/[batch]/route.ts` is the printed-QR-code redirect, and it's meant to outlive whatever `mybarbets.com` currently points at.** Physical cards/stickers encode `https://mybarbets.com/go/<batch>` (`batch` identifies the print run, e.g. `card`) — that URL is what's on the printed material, so it can never change. Everything about where it actually sends people lives behind that stable path instead: Android UAs go straight to the live Play Store listing with a `referrer` query param (`utm_source=qr&utm_medium=print&utm_campaign=<batch>`), which the Play Install Referrer API lets the app read back after install for real per-batch attribution with no third-party service; iOS goes to `APPLE_APP_STORE_URL` (an env var, unset until Apple's review clears) with an analogous `pt`/`ct` campaign token, falling back to a download page for any non-mobile scan in the meantime. **The canonical copy of this handler now lives in the `barbets-www` project**, since that is what `mybarbets.com` resolves to; the copy in this repo is a transitional duplicate that gets deleted once the domain has moved (see the Deployment section). The Android branch is byte-identical in both on purpose: the `referrer` value is parsed back inside the native app via the Play Install Referrer API, so changing its shape silently breaks attribution for every card already printed, with no error anywhere. The already-printed QR codes keep working unchanged through both the domain move and Apple's listing going live.

## Keeping this document current (read this if you're an agent working in this repo)

**This file is the canonical description of how Barbets works, and it is expected to stay that way. Updating it is part of the change, not a follow-up chore.** It is deliberately written as prose that explains *why* a non-obvious choice was made, because the "why" is the part that can't be recovered from reading the code later — a future reader can always see *what* `finalize_market` does, but not that turnout apathy upholds the proposal because voiding made challenging a free undo for a losing bettor.

Update this doc in the **same change** that touches the code whenever you:

- add, rename, or delete a Postgres function, table, column, enum value, or RLS policy — the "Data model" and "Postgres functions" sections are meant to be exhaustive
- add a new `notification_events` event type, or edit any push copy (the copy table below must match `supabase/functions/send-push/index.ts` exactly)
- add a new top-level route, `lib/actions/*.ts` file, or `lib/*.ts` module — reflect it in the "Project structure" tree
- change a money rule, a privacy rule, or anything that touches `is_market_visible()`
- introduce a new authority model, access gate, or external integration (see "Platform admin, feedback, and access gates" below for the current set)
- make a decision you had to think about, especially one where the obvious approach was wrong — that belongs in "Notable design decisions worth remembering," with the reasoning, not just the outcome
- **discover that this doc is already wrong or silent about something.** Fix it then and there. Drift is what makes a doc stop being trusted, and an untrusted doc is worse than none.

Small mechanical changes (a copy tweak, a Tailwind class, a component refactor that changes no behavior) don't need an entry. When in doubt about whether something is doc-worthy: if a new contributor would be surprised by it, or if you'd have to re-derive it by reading three files, document it.

If you're an agent and the user asks for a change that clearly warrants a doc update, do the doc update as part of the work and say so — don't ask whether they want it.

## Tech stack

- **Next.js 16** (App Router, React 19, TypeScript) — server components for reads, Server Actions for all mutations
- **Supabase** — Postgres, Auth, Row Level Security, Storage (one private bucket), Edge Functions (Deno), pg_cron + pg_net for scheduled jobs
- **Tailwind CSS v4** — CSS-based `@theme`, no `tailwind.config.ts`
- **Vercel** — hosting, deploys via `vercel --prod`
- **Vitest** — integration tests that hit the real hosted Supabase project as real logged-in users (no mocks)

## Data model

Postgres enums define the closed vocabularies for the state machines:

- `market_type`: `yes_no` | `over_under` | `multiple_choice`
- `market_status`: `pending_sponsor` → `open` → `closed` → `proposed` → (`disputed`) → `resolved` | `voided`
- `bet_side`: `yes` | `no` | `over` | `under` (what you actually bet/vote/propose on for `yes_no`/`over_under` markets — `multiple_choice` uses an `option_id` instead, see below)
- `market_outcome`: `bet_side` + `void` (what a `yes_no`/`over_under` market resolves to, or a proposer can directly propose; a `multiple_choice` market resolves via `outcome_option_id` instead, leaving `outcome` null unless the result is VOID)
- `ledger_entry_type`: `seed` | `bet` | `payout` | `refund`
- `membership_status`: `active` | `dormant` | `left` | `removed`
- `season_status`: `active` → (`winding_down`) → `archived` → `intermission` → next season's `active`. `season_length`: `1m` | `2m` | `3m` | `custom` (a specific owner-picked end date/time) | `manual` (no fixed end)

Core tables: `users`, `groups`, `group_settings`, `memberships`, `seasons`, `season_optins`, `season_optouts`, `season_results`, `markets`, `market_subjects`, `market_options`, `bets`, `ledger`, `resolution_proposals`, `challenges`, `votes`, `market_reactions`, `resolution_clarifications`, `group_titles`, `push_subscriptions`, `notification_events`, `sweep_failures`, `app_admins`, `feedback`, `invite_code_attempts`.

The last five are the app's **zero-policy tables**: `notification_events`, `sweep_failures`, `app_admins`, `feedback`, and `invite_code_attempts` all have RLS enabled with no client-facing policy of any kind, so no `authenticated` role can read or write them at all — only `service_role` and SECURITY DEFINER functions get in. That's the same deny-by-default posture as everything else here, just taken to its endpoint (there is no legitimate client read of any of the five, and for `invite_code_attempts` a client that could UPDATE its own row could reset its own rate limit).

`sweep_failures` is a diagnostic log, one row per `(sweep, subject_id)` that `expire_stale()` failed on, with an `attempts` counter rather than a row per failure. `subject_id` is a market, season or group id depending on which sweep it came from, so it deliberately carries **no foreign key** — there's no single table to point at, and a cascade would delete the evidence at exactly the moment it's worth having.

**Non-owner members get read-only visibility into `group_settings`** (betting on/off, token allocation, time zone, season status, whether hedged betting is allowed, whether endorsement is required, the challenge/resolution window, the payout-distribution setting below) via the settings page — the owner is still the only one who can call `update_group_settings`; everyone else just gets to see what it's currently set to instead of it being owner-only screen real estate. Both `betting_enabled` and `seasons_enabled` are one-way switches — `update_group_settings` rejects flipping either back off once on, same reasoning both times: pausing things is what `end_season()` (voids+refunds open markets, opens intermission) is for, not a settings toggle. For a seasons-enabled group, `betting_enabled` stops mattering to `create_market()` entirely once the first season starts — see the per-season betting gate below. `allow_hedged_bets` (default on) and `require_endorsement` (default on) both stay freely reversible in either direction — each only gates a single future call (`place_bet`, `create_market`'s `pending_sponsor` routing) with no in-flight state either direction could corrupt, unlike the two one-way switches.

**A group can pick a logo** (`groups.avatar_key`) from the fixed set in `lib/avatars.ts`, served straight out of `public/avatars/` as ordinary static assets. It's deliberately plain text with only a shape check (`^[a-z0-9-]{1,32}$`), not an enum or a lookup table: the art ships in the bundle, `lib/avatars.ts` is already the list that decides what renders, and a second copy of that list in Postgres would mean a migration every time a PNG is added or retired. An unrecognized key degrades to the group's initials tile (`groupAvatarSrc()` returns null) rather than erroring or rendering a broken image. `set_group_avatar()` is owner-only; `components/ui/GroupAvatar` is the one component that decides avatar-or-initials, used by the groups hub, BottomNav's switcher, the profile switcher, and the group hub's own heading.

**Names have length caps, enforced in Postgres, not just in the input.** A group name (`create_group`, `rename_group`) is capped at 60 characters, a season name (`rename_season`, `20260811140000_token_allocation_and_season_name_caps.sql`) at 60 as well, a market title (`create_market`) at 140, all measured and stored after `trim()`. The group name and market title also reject a blank/whitespace-only value (the columns are `not null`, which a string of spaces satisfies); a season name does not, because `seasons.name` is nullable and clearing it is how you get back to the "Season N" display fallback. `lib/limits.ts` holds the numbers so the create/rename inputs' `maxLength` and the create-market form's near-the-cap counter can't drift from what the functions actually accept; the browser attribute is the polite stop, the function's check is the real one. (The other free-text cap, the over/under `unit`'s 10 characters, stays in `lib/units.ts` next to the rest of the unit logic rather than moving here.) 60 matches what the group rename and season rename boxes already allowed on the client, so no name typed through the UI can be too long. 140 for a title is deliberately generous — a title is a question, and the specifics of what counts as a win belong in `markets.description` (the resolution criteria), which stays uncapped since nothing renders it in a constrained space. No CHECK constraint backs either: the message a constraint violation produces would come back through `runRpc()` as an unmapped `unknown` error instead of the friendly `invalid_operation:` copy, and every write to both columns already goes through a SECURITY DEFINER function.

**The token allocation is bounded to 1..1,000,000** (`group_settings.seed_amount`, checked in both `create_group` and `update_group_settings`, `lib/limits.ts`'s `TOKEN_ALLOCATION_MIN`/`MAX`). The ceiling exists because the allocation sets the scale of every number the group ever renders — balances, bet amounts, leaderboard figures, payouts, push bodies — and a keypad slip on group creation is permanent in a way no other setting is. The floor is 1 rather than 0 because the allocation input strips non-digits as you type, so an emptied box submits `Number('') = 0`, which used to create a group where nobody can ever place a bet. Two things about it worth knowing:
- **`update_group_settings` only applies the bound when the submitted value differs from the stored one.** The settings form re-submits every field on every save, so an unconditional check would lock the owner of a pre-existing over-cap group out of editing their time zone (or anything else) until they worked out that the allocation was the field being rejected. Grandfathered figures keep working and can only be moved back into range, never further out.
- **The settings input's `defaultValue` is deliberately not clamped**, only its `onChange`. Clamping the initial value would mean opening the form for an unrelated change and saving it quietly rewrote a grandfathered allocation down to the cap.

**Invite codes are 4 characters, with no prefix.** They used to carry a literal `BB-`, dropped in `20260810140000_invite_codes_drop_bb_prefix.sql` (which rewrote every existing code in place, so there is only ever one live format). Printed cards and already-shared `/join/BB-XXXX` links keep working because `lib/inviteCode.ts`'s `normalizeInviteCode()` strips a legacy prefix on the way in, applied at the three places every join funnels through: the `/join/[code]` route, `joinGroup()`, and the hub's paste handler. No Postgres function knows the old format exists.

**Guessing at invite codes is rate limited in the database, at 10 misses per user per hour** (`invite_code_attempts`, `20260813130000_invite_code_rate_limit.sql`). A 4-character code is short enough to be worth guessing at, and two functions will confirm a guess: `get_group_by_invite_code()` names the group, `join_group()` walks you in. Both are granted to `authenticated`, so the surface that actually matters is the PostgREST endpoint with any signed-up account's JWT, not the two screens in front of them — a limit in the Next.js layer would guard neither. One budget covers both functions, so spending it on previews leaves none for joins. Only a **miss** counts: previewing or joining with a code that really exists is what an invited person does, so no amount of legitimate use can lock someone out of their own group. The counter is one row per user (created on their first miss, cascading away with the account), not one row per attempt, so it needs no retention sweep. Two things follow from this that are easy to trip over later:

- **Neither miss path raises any more**, because a `RAISE` aborts the transaction and would roll back the very increment that makes the limit work — a wrong code can be counted or be raised, never both. `get_group_by_invite_code()` already signalled a miss with zero rows; `join_group()` now returns **zero rows** too (it was changed to `returns setof memberships` for exactly that) instead of `not_found: invalid invite code`, and `joinGroup()` in `lib/actions/groups.ts` turns the empty result into the same friendly copy. It is worth knowing why it isn't a NULL return, since that was tried first and is the obvious shape for a function returning one row: a plpgsql function declared `returns memberships` that returns NULL hands PostgREST a NULL *composite*, which serializes as a row of all-null columns rather than as `null`, so every `if (!data)` check in the app reads it as a successful join with a null `group_id`. Zero rows is the only signal that can't be mistaken for a value. Everything else `join_group()` rejects (removed member, nickname taken, group not accepting) still raises exactly as before, since all of those require a code that really exists. Being over the limit still raises (`invalid_operation`, carrying the real minutes left) — there's nothing left to write at that point for the abort to undo.
- **`get_group_by_invite_code()` had to become VOLATILE plpgsql.** PostgREST runs a `STABLE` function inside a read-only transaction, so as a `stable sql` function it could not have written the counter at all. It kept the same signature; only the language and volatility changed. (Its return shape did change later, in `20260814100000_invite_preview_avatar.sql`, to add `avatar_key` — see below.)

The `/join/[code]` page is the one read path that reads a Postgres error itself rather than going through a Server Action: a wrong code is not an error there (zero rows), so an error can only be the rate limit, and anything that isn't `invalid_operation` is rethrown to the error boundary rather than being dressed up as a bad invite. `lib/errors.ts` exports `friendlyMessage()` for exactly that one call site.

**`get_group_by_invite_code()` also returns `avatar_key`** (`20260814100000_invite_preview_avatar.sql`), so the `/join/[code]` confirm screen can show the group's actual chosen avatar instead of always falling back to `GroupAvatar`'s initials monogram. This is deliberately different from the rest of the function's stance of showing a non-member as little as possible: `avatar_key` isn't group data, it's a pointer into the fixed, app-authored icon set in `lib/avatars.ts`, identical for every group and never user-supplied, so revealing it to a non-member carries none of the privacy weight that (say) member lists or balances would.

**The keyspace being protected got 16x bigger at the same time** (`20260813140000_invite_code_alphabet.sql`). `_generate_invite_code()` used to draw from `md5()`, which meant every code ever minted was hex: 16 possible characters and a real keyspace of 16^4 = 65,536, not the ~1.7 million a 4-character alphanumeric code looks like it has. That was never a decision, it's just what `md5()` emits. New codes now come from a deliberate 32-character alphabet, **digits 2-9 and A-Z without I and O** — 0/O and 1/I are left out because a code gets read out loud in a bar and typed off a printed card, and those are the two pairs that come back as the wrong character. 32^4 = 1,048,576. Two supporting details:

- **Existing codes are deliberately not rewritten**, unlike the `BB-` prefix removal. There's nothing to reconcile this time: a code is looked up by exact match, and every old hex code is still valid `A-Z0-9` that `normalizeInviteCode()` and the four input boxes already accept. Rewriting would kill every `/join` link and printed card already in the world to buy nothing but tidiness. So an old code may contain a `0` or a `1`; a new one never will.
- **Randomness comes from `gen_random_uuid()`'s CSPRNG, not `random()`** (a per-session PRNG, never the right source for something whose whole job is being unguessable). Only bytes 0-3 of the UUID are used, since bytes 6 and 8 of a v4 UUID carry fixed version/variant bits. Each byte is taken modulo 32, which is exactly uniform because 256 divides evenly by 32 — keep the alphabet a power-of-two length if it ever changes. `pgcrypto`'s `gen_random_bytes()` would be the more direct tool but lives in the `extensions` schema, and these functions run with `search_path = public`; `uuid_send`/`get_byte`/`gen_random_uuid` are all `pg_catalog` builtins, so this needs no extension.

**Identity is per-group, not global.** `users` carries only `id` (auto-created on first sign-in, no separate claim step) and an unused `display_name`. What you're actually called and @mentioned as is `memberships.nickname` — one member can go by a different nickname in a different group. Set once on `create_group`/`join_group` (required on any path that inserts a brand-new membership row, or reactivates a `left` one — see below; reactivating a `dormant` row or no-op'ing on an `active` one keeps the existing nickname untouched instead), changeable later via `update_nickname()`. Unique per group among memberships that are neither `removed` nor `left`, via a partial index (`memberships_group_nickname_unique`) rather than a plain constraint — a `dormant` member's nickname stays reserved for them (they're still meaningfully "in" the group, just sitting out a season), while a `removed` or `left` member's frees up immediately for someone else.

`group_settings.timezone` is an owner-set IANA zone name, purely informational: it's shown as a caption next to every "betting closes" field/display so members know what zone the person who set the closing time meant. It does not change how `datetime-local` inputs are interpreted (still the visiting browser's own local time) — there's no way to make that input read an arbitrary zone without real timezone-math, which would be a materially bigger feature.

**Over/under markets** can carry an optional `unit` (`markets.unit`, free text, 10 characters or fewer — `lib/units.ts`'s `OVER_UNDER_UNIT_MAX_LENGTH`, tightened from 12 in `20260810170000_name_and_unit_length_limits.sql` because the unit renders inline beside the line; markets created before that keep whatever they stored, since `create_market` is the only place a unit is ever validated) so the line reads as "5.5 min" instead of a bare number — `create_market()` rejects a non-null unit on any other market type. `lib/units.ts`'s `formatLine()` is the one shared formatter (`$`/`£`/`€` prefix the number, everything else trails it), used everywhere the line is displayed: `MarketCard`'s odds-bar center badge, the market page's "Line" stat tile, and the reveal ticket. The create-market form offers a short preset list (`$`, `min`, `hr`, `pts`, `%`, with `£`/`€` behind a long-press on `$`) plus a free-text "Custom" field for anything else.

**A line can also be a date or time, not just a number.** The create-market form's "Number / Date / Time" toggle repurposes `unit` itself as the format marker (`'date'`/`'time'`, mutually exclusive with a real display unit — a line can't be both "a date" and "5.5 min") rather than adding a schema column: a date is stored as whole-day Unix epoch seconds at UTC midnight (`lib/units.ts`'s `parseLineInput()`), a time as minutes since midnight. `formatLine()` special-cases both back into a readable date/time, so every existing display call site picked this up with zero changes. This is purely an input/display convenience — `propose_resolution`'s `p_outcome` (over/under/void) is always a direct human choice, never computed from `line`, so nothing money-critical reads `line` as anything but an opaque number.

**Multiple choice markets** add `market_options` (2–10 rows per market: `label` + `sort_order`, enforced in `create_market()`). Every place that used to carry a single `bet_side`/`market_outcome` value grew an `option_id` sibling instead — `bets.option_id`, `markets.outcome_option_id`, `resolution_proposals.proposed_option_id`, `votes.voted_option_id` — with exactly one of each pair ever populated on a given row, enforced by a same-table CHECK constraint (`..._xor_option`). VOID always goes through the original `outcome`/`bet_side` column as the literal `'void'`, never through `option_id` — VOID isn't an option, it's the automatic tie/zero-turnout fallback or an explicit proposal/ballot choice, same as for the other two types. Each option is a single field: plain text, or a leading `@nickname` that `create_market()` resolves against `memberships.nickname` in that group and attaches as the option's one subject (at most one subject per option, by construction — a label either starts with `@` or it doesn't). `market_subjects.option_id` is nullable and stays null for `yes_no`/`over_under` (market-level subjects, unchanged). Privacy stays market-level regardless of option — `is_market_visible()` matches on `market_id` alone, so being @'d in any single option still hides the whole market (seeing any option would reveal the market exists).

### The privacy choke point

Every table that can leak a subject's existence is gated by one function:

```sql
create function is_market_visible(p_market_id uuid, p_user_id uuid default auth.uid())
returns boolean ... security definer as $$
  select exists (
    select 1 from markets m
    join memberships mem on mem.group_id = m.group_id and mem.user_id = p_user_id
    where m.id = p_market_id
      and (
        not exists (select 1 from market_subjects ms where ms.market_id = m.id and ms.user_id = p_user_id)
        or m.status in ('resolved', 'voided')
      )
  );
$$;

create view visible_markets with (security_invoker = true) as
  select m.* from markets m where is_market_visible(m.id, (select auth.uid()));
```

Every RLS policy on `markets`, `market_subjects`, `bets`, `resolution_proposals`, `challenges`, `votes`, and `market_reactions` calls this same function. `security_invoker = true` on the view is load-bearing — without it, the view would run with the *view owner's* privileges instead of the querying user's. RLS is deny-by-default: no table has a client-facing INSERT/UPDATE/DELETE policy at all. The only way to change money- or market-state is through the SECURITY DEFINER functions below.

**Every `auth.uid()` reached from a policy is written `(select auth.uid())`** (`20260812100000_rls_initplan_auth_uid.sql`, which rewrote 13 of the 21 policies plus the view). A bare `auth.uid()` in a `USING`/`WITH CHECK` expression is a function reference sitting inside a per-row filter, so Postgres calls it once for every row it tests; wrapping it in a scalar subquery makes it an uncorrelated InitPlan, evaluated once per statement. On `bets` (scanned on every group page) and on everything gated by `is_market_visible()`, that's the difference between one JWT decode and one per row. Four details are worth keeping:

- **Seven of the eight untouched policies had no expression to hoist.** `groups`, `group_settings`, `memberships`, `seasons`, `season_optins`, `season_results` and `season_optouts` all reach `auth.uid()` only from inside `_caller_is_active_group_member()`, which is SECURITY DEFINER and therefore never inlined into the query. Wrapping would have meant copying that function's `status not in ('removed', 'left')` rule into seven policies, and *that* rule drifting is a privacy bug, not a performance one. (The eighth is `users_select_all`, which is `using (true)`.)
- **Seven policies referenced `auth.uid()` without containing the string.** The `is_market_visible(...)` policies leaned on the function's `p_user_id uuid default auth.uid()`, which is inlined into the query as a bare per-row call exactly as if it had been written out — invisible to any audit that greps policy text. **That default cannot itself be wrapped** (Postgres rejects a subquery in a parameter default outright), so each policy now passes `(select auth.uid())` explicitly. The default stays for any non-policy caller.
- **`ALTER POLICY`, never `DROP` + `CREATE`** — see the design-decision note below on why the `create policy` statements in the migration history are not the current definitions.
- The same migration is also the fourth `visible_markets` refresh (see the note in "Notable design decisions"), which incidentally picked up `closing_nudge_sent_at`, missing from the view since `20260810162000`.

A query filtered by RLS that comes back empty always means the same thing to the client — 404, never a distinguishable 403 — whether the row genuinely doesn't exist or you're a hidden subject. `lib/errors.ts`'s `notFoundIfEmpty()` enforces this at every route.

## Postgres functions (the only way to mutate anything)

All are `SECURITY DEFINER`, `SET search_path = public`, and explicitly `REVOKE`d from `public`/`anon` then `GRANT`ed only to `authenticated` (Supabase auto-grants EXECUTE by default, which would otherwise be an over-permissive hole).

- **`create_group` / `join_group` / `remove_member` / `leave_group`** — group membership. Leaving is self-service: it no longer refunds the leaver's own open bets (those stakes stay in their pools and settle normally into their now-`left` membership's balance), but still voids+refunds any market where the leaver is a **subject** (unavoidable — the market's premise left the room). A self-service leave sets status to `left` — distinct from `dormant` (see the season-opt-in bullet below, for a member who just joined mid-intermission and is still very much "in" the group) — which, via the same `status <> 'removed'`-style checks every RLS choke point (`_caller_is_active_group_member`, `is_market_visible`) and eligibility gate now also excludes, makes the group and everything in it disappear from the leaver's own queries immediately, same as `removed` does, and frees their nickname up (see above) — but unlike `removed`, `left` can still rejoin. Rejoining a `dormant` membership reactivates it in place with whatever balance is already sitting there, same reserved nickname, no re-validation needed. Rejoining a `left` membership also reactivates in place and never reseeds, but since the nickname was released, `join_group` re-validates/applies whatever nickname the join form sent (the same one a brand-new join collects) rather than assuming it's still free. A `removed` membership (owner-initiated only) can never rejoin at all. `remove_member` still refunds the removed member's own open bets (they didn't choose to leave) and additionally rotates the group's invite code in the same transaction, so the removed member's known code is dead going forward — leaving never rotates the invite code, since nothing about a voluntary leave requires invalidating it for everyone else. Seeding happens in exactly two places: first-time join, and season start for opted-in members. A `left` member who actually bet before leaving still shows up on the group's leaderboard (their historical record stays honest) even though they've vanished from every "who's currently here" surface (profile, the groups hub, the settings/intermission rosters) — a `left` member who never bet leaves no trace anywhere. One deviation from the "business-rule errors raise" convention lives in `join_group`: a code matching **no** group returns zero rows (hence `returns setof memberships`) instead of raising, so the invite-code rate limit's counter survives the transaction (see the invite-code rate limit above, and the design-decisions note).
- **`create_market` / `sponsor_market`** — by default a market needs two humans: whoever creates it, and a *different* member who endorses ("sponsors") it before it opens. Unsponsored markets auto-expire once `closes_at` actually passes with nobody having endorsed it, or 24h after creation, whichever comes first — since a `pending_sponsor` market can't have any bets yet, this expiry is a plain void, nothing to refund. `sponsor_market` separately refuses to endorse inside the last 5 minutes before `closes_at` (there'd be no real time left to bet), but that's a gate on the action, not an early sweep — a market sitting at, say, 3 minutes-to-close just goes un-sponsorable and waits for `closes_at` to actually pass rather than getting force-voided early. **The owner can turn this requirement off** (`group_settings.require_endorsement`, default on) for a small, high-trust group where waiting on a second person is friction with no real check behind it — `create_market()` then inserts the market straight into `open` (no `sponsor_id`, `market_opened` fires immediately instead of `market_needs_endorsement`), skipping `pending_sponsor` entirely. Subject count is still capped at `member_count - 2` regardless of this setting (enough non-subject members left for a creator and a separate endorser — both of whom can also bet on it themselves) — deliberately *not* relaxed to `member_count - 1` when endorsement isn't required, since touching that cap's math felt like too much risk to a privacy-adjacent invariant for what this setting is actually for; revisit if a `require_endorsement = false` group ever really runs into it. For `multiple_choice`, `create_market` instead takes an ordered list of 2–10 option strings (plain text, or `@nickname`), and both the creator/sponsor exclusion and the subject-count cap apply to the **union of distinct users resolved across every option** — a nickname can only be @mentioned in one option (checked case-insensitively, so `@dan` and `@Dan` collide even though they're distinct label text).
- **`place_bet`** — locks the market row (serializes against `expire_stale()` concurrently closing it) and the bettor's membership row. A bet can be for any amount from 1 up to the bettor's full current balance (no percentage cap). Dormant members and subjects can't bet. `multiple_choice` bets carry an `option_id` instead of a `side`; by default a member may hedge across multiple sides/options in the same market, but the owner can turn `group_settings.allow_hedged_bets` off, which rejects a bet on a side/option that's `is distinct from` every side/option the member already holds in that market — a same-side top-up (identical side/option to an existing bet, just more staked) always stays allowed either way, since only genuine hedging is the target.
- **`propose_resolution`** (challenge window starts) → **`challenge_resolution`** (moves to a secret ballot) → **`cast_vote`** → **`finalize_market`**.
  - `propose_resolution` may fire while a market is still `open`, not just `closed` — betting locks the instant the proposal commits (the same market-row lock `place_bet` already takes makes this race-safe). `closed_at` records when betting actually locked, independent of `closes_at` (which stays the *latest* possible close), so the UI can show "closed early by proposal." This early-close path emits only `resolution_proposed`, not also `market_closed` — recipients don't need "odds are live" and "a resolution was proposed" as two separate pushes for the same moment. The natural auto-close path (`expire_stale()` reaching `closes_at` with no proposal yet) is unaffected and still emits `market_closed` on its own, since nobody's proposed anything at that point.
  - A vote resolves either when the vote window elapses, *or* the moment every eligible (non-subject, non-removed) member has voted — whichever comes first. `multiple_choice` ballots list every option plus VOID. The challenge window and the vote window share one owner-configurable duration, `group_settings.resolution_window_hours` (default 8, 0.5-10 in half-hour steps — the settings UI recommends at least 2h without enforcing it) — `challenge_resolution()`, `cast_vote()`, `finalize_market()`, and `expire_stale()`'s two auto-finalize sweeps all read the same column instead of a hardcoded value.
  - **Turnout rule**: zero ballots cast, or a tie for first place that *includes* the originally proposed outcome, upholds the proposal instead of voiding — apathy or indecision defaults to what was proposed, so challenging is only worth it if you can actually rally votes against it. A tie that *excludes* the proposal, or an explicit VOID majority, still resolves as **voided** (full refund to everyone) — the group actively disagreed with the proposal but couldn't agree on an alternative.
  - `propose_resolution` also takes an optional `p_photo_path`, a proof photo the proposer attaches at proposal time (`ProposeResolutionCard`, compressed client-side in `lib/compressImage.ts`, no dependency). It rides untouched through a challenge/vote (`resolution_proposals` is never re-inserted for a market, only its `finalized`/`votes_revealed_at` columns get updated) and stays visible after resolution — except on a `voided` market, since a void means the group never settled on what the photo was supposed to prove. The photo itself lives in the private `resolution-proofs` Storage bucket, which has zero `storage.objects` RLS policies (deny-by-default, same posture as every other table here) — every read and write goes through `lib/actions/resolution.ts`'s `proposeResolution()`/`getResolutionProofUrl()`, which re-check the exact same `is_market_visible`-backed RLS (via `resolution_proposals`/`visible_markets`, queried as the requesting user) before ever reaching for the service-role client to upload or sign a URL. One choke point, not two.
- **`request_clarification` / `update_resolution_criteria`** — lets a non-creator member flag that a market's resolution criteria (`markets.description`) is unclear, and lets the creator tighten the wording in response. Not secret while pending: `resolution_clarifications` is visible to everyone who can see the market (same `is_market_visible()`-gated, select-only RLS posture as `resolution_proposals`/`challenges`), so the question shows up on the market page like a proposal justification does. `update_resolution_criteria` is strictly reactive, never a free edit — it rejects a non-creator caller (`forbidden`, not subject-masked, since the creator can never be a subject of their own market by construction) and requires at least one existing row in `resolution_clarifications` for the market (every row in that table is currently-pending by construction — see below). A successful update **deletes every row** for that market in the same transaction, not just marks them answered — nothing lingers as history once addressed; the new `description` text is the only trace an answer ever happened. Both actions are gated to `status in ('open', 'pending_sponsor')`, checked before any other business-rule check in `update_resolution_criteria`, so the gate holds even when a pending request still exists (e.g. an early resolution proposal locked betting mid-conversation). `pending_sponsor` was added to that pair in `20260811120000_clarification_before_endorsement.sql`: the endorsement gate exists so a second member can check the question is fair and unambiguous before betting opens, and refusing to let that member ask what a vague criterion means until *after* they had vouched for it left them only "endorse it anyway" or "walk away," neither of which gets the wording fixed. Widening both halves of the exchange is what makes the endorsement screen's "Ask for a clarification" panel a real third option. Nothing else about the pair moved — still non-creator-only to ask, still creator-only to answer, still requires a pending row to answer against, and every later status is still rejected outright. `clarification_requested` is single-recipient (the creator only, via a `get_event_recipients` carve-out like `member_joined`/`impressive_bet`); `criteria_updated` reaches everyone else who can currently see the market, same as `market_closed`. A market the current user created with an open row in `resolution_clarifications` also surfaces as a small "!" badge next to the status pill on the market card/detail page, computed by an inner-join existence check against `resolution_clarifications`, since presence of any row already means pending. On the market page itself, asking is a circular "?" trigger in the resolution criteria card's corner that opens a small popover (explaining what asking does and what happens next) — the same overlapping-popover treatment `ReactionBar` uses on the reveal ticket, just re-themed for a light card instead of the dark ticket background.
- **Parimutuel payout** (`finalize_market`, the money-critical core): each winning bet's base payout is `floor(bet.amount * total_pool / winning_pool)`. The leftover "dust" from flooring goes entirely to the single largest winning stake (ties broken by earliest bet, then bet id). This guarantees `sum(payouts) == total_pool` exactly — no tokens created or destroyed. A one-sided market falls back to every bet winning outright (dust and all, same formula). The winner-filter (`side = v_winning_bet_side OR option_id = v_outcome_option_id`) is a single unified expression across all three market types — exactly one of those two variables is ever non-null for a given resolution, so `multiple_choice` reuses the identical payout/dust code path with no branching.
- **Winning side has zero bets ("everyone loses")** — nobody predicted the outcome that actually happened. By default this is a full refund of every stake, same as VOID. The owner can flip `group_settings.distribute_payout` on instead (default off; a single `creator_payout_pct`, default 25): the market's creator takes their cut of the real stakes on that market, and the whole remainder tops up `bonus_pool` equally across every other currently-*open* market in the group — a market absorbs its `bonus_pool` into its own `total_pool` the same way real stakes are absorbed, whenever it next resolves (win, its own zero-winner-pool split, or void). If there's no other open market to receive the remainder, the whole thing holds in `groups.pending_bonus_pool` instead — a group-wide holding pool — regardless of whether this market had any real bettors of its own; the remainder never routes back to the specific bettors who lost it, only ever forward. `refund_all_bets()` (used here when the setting is off, by every VOID resolution, and by season-end/member-removal force-voids) always drains a market's `bonus_pool` the same way on its way out — split across other open markets, or into `pending_bonus_pool` if none — so inherited bonus money can never get stranded on a market that never resolves to a real winner. That "other open markets" set explicitly excludes the market being refunded (`id <> p_market_id`), which matters because several callers refund *before* flipping the status and so are still `open` at that moment — see the design-decisions note below. **There is no endorser cut** — `group_settings.endorser_payout_pct` was dropped in `20260810130000_remove_endorser_payout_cut.sql`. It was a second number where one would do (nobody reasoned about it; the creator's share was the only real decision), and it rewarded a role that costs one tap and carries no risk. `payout_breakdown` keeps its `endorser_cut` key, written as a literal `0` from then on, purely so markets that resolved before the change still render honestly on the reveal page. The settings UI now shows the creator % as the only editable field plus a read-only "Open markets %" derived from it, which also makes the old "these can't sum past 100" error state structurally impossible. Whenever this branch fires, `markets.payout_breakdown` (jsonb: `creator_cut`/`endorser_cut`/`other_markets_cut`/`held_in_group_pool`, exactly one of the last two ever non-zero) records precisely where the pool went, for the reveal page — this can't be reconstructed from the ledger after the fact, since a `bonus_pool` transfer to another market (or into `pending_bonus_pool`) is a pot-level column update, not a balance change, so it never gets a ledger row. Null for every other `finalize_market()` path.
  - **`groups.pending_bonus_pool` waits for the next market, not the next payout.** `create_market()` seeds a brand-new market's `bonus_pool` from whatever's sitting in `pending_bonus_pool` the moment it's created (locking the `groups` row first, so two concurrent creates can't both claim it), zeroes the pool, and stamps `markets.carried_bonus_pool` with the seeded amount — immutable after creation, purely so the market page can note "started with N bonus tokens carried over from an earlier resolution" (`bonus_pool` itself can keep growing after that, same as any other market's). If the season archives before any market claims it, `_finalize_season()` splits whatever's left evenly across currently-*active* members instead (dust to whoever's currently in the lead, same tie-break as the champion snapshot) — this is the one place a `payout` ledger row has no `market_id` (see below), since the season that would have received it is already gone by the time this fires.
- **`void_market_by_owner`** — an unconditional owner kill switch for one market, at any stage before it's already `resolved`/`voided` (`pending_sponsor` through `disputed`). Refunds every stake via the same `refund_all_bets()` helper VOID resolutions and season-end/member-removal force-voids already use (so it also correctly drains any inherited `bonus_pool`), then emits `market_voided` instead of `market_resolved` — a deliberately different push so recipients know the owner stepped in rather than assuming a proposal/vote ran its course. Not reachable if the owner happens to be the market's subject (`not_found`, same 404-not-403 rule as everywhere else).
- **`void_market_by_creator`** — the fallback for the one case `void_market_by_owner` can never reach: the owner is themselves `@mentioned` as the market's subject, so `is_market_visible()` hides the market from them before ownership is even checked. Gives the market's *creator* (who by `create_market`'s own constraint can never be a subject) an equivalent on-demand override, strictly gated to that one scenario — it 404s like every other subject-adjacent function, and refuses outright (`invalid_operation`, not a silent no-op) if the owner isn't actually a subject of this specific market, since the owner is still meant to be the one calling the shots whenever they're able to. Every other stuck-market path still resolves eventually on its own (a normal vote can VOID it, or `end_season()` force-voids everything), just not on demand.
- **`end_season` / `start_season` / `opt_in_season` / `opt_out_season` / `cancel_season_optout` / `open_season_betting` / `rename_season`** — seasons unify continuous play, long seasons, and short one-off event nights into one system: the only real differences are duration, and whether the group bothers with the ceremony below.
  - **Wind-down instead of instant force-void.** `end_season()` immediately force-voids any market that never got a resolution proposed (`pending_sponsor`/`open`/`closed` — nobody started the clock, nothing to wait on), but a market already `proposed`/`disputed` is left alone to run its normal challenge/vote timers. If nothing was in flight, the season archives synchronously in the same call (the common case, and the only case before this). If something was, the season instead moves to `winding_down` (a `seasons.wind_down_deadline`, `resolution_window_hours` past season end, is the hard cap — long enough for whichever one phase, challenge or vote, the in-flight market still has left) — `create_market()`'s `status = 'active'` lookup simply doesn't match `winding_down`, so no new markets can be created during it with no extra code. `_finalize_season()` (the shared internal helper doing the snapshot/archive/next-intermission-row work `end_season()` used to do inline) gets called from three places: `end_season()` itself when nothing's in flight, `finalize_market()`'s tail hook the instant it clears the *last* in-flight market of a `winding_down` season (so a season doesn't sit around for up to a minute waiting on the next cron tick), and `expire_stale()`'s hard-cap sweep, which force-voids anything still unresolved once `wind_down_deadline` passes and archives from there. `season_ended` is emitted with the real actor (the owner who clicked "End season now") only on the synchronous fast path; the deferred paths have no honest single actor and emit with `actor_id = null`.
  - **Opt-out by default, not opt-in.** A currently-**active** member is included in the next season automatically — `opt_out_season()`/`cancel_season_optout()` (writing to `season_optouts`, presence = "sitting this one out") is how they preemptively skip it, mirroring `opt_in_season`'s existing dual intermission/already-active behavior in the opposite direction. A currently-**dormant** member (a prior opt-out, or just joined mid-intermission) stays dormant unless they explicitly ask in — that's still exactly `opt_in_season()`/`season_optins` (presence = "asking to be swept in"), completely unchanged by this. The two tables are deliberately not one inverted table: `_cleanup_departing_member()` (shared by `leave_group`/`remove_member`) already deletes a departing member's `season_optins` row on every departure, and reusing that same delete for an "opted out" table would have silently *un-excluded* them instead — `start_season()`'s reseed rule is a union of `(active AND no season_optouts row)` OR `(dormant AND has a season_optins row)`, so a plain dormant member with neither row is correctly left alone either way.
  - **Betting starts paused every season**, including a group's very first one — `seasons.betting_open` (default `false`) is a separate gate from the group-level `betting_enabled` for exactly the groups where it matters (`seasons_enabled = true`); `open_season_betting()` (owner-only, once per season) is the explicit "go" that lets the owner see who's actually playing before any market can be created. Continuous (non-seasons) groups are untouched — `betting_enabled` alone still gates them.
  - **Duration**: `1m`/`2m`/`3m` (relative to `started_at`) or `custom` (`group_settings.season_custom_ends_at`, a specific date/time — useful for a single weekend or a summer with a real end in mind) get frozen onto `seasons.ends_at`/`season_length` the moment `start_season()` activates them (same freeze-at-start pattern `seed_amount` already used), which is also what `create_market()` checks `p_closes_at` against and what `expire_stale()`'s timed-end sweep reads — nothing here is recomputed live from `group_settings` mid-season, so editing settings mid-season can't retroactively move the current season's end. `manual` seasons have `ends_at is null`: no auto-end, no `closes_at` ceiling. A `custom` date that's since lapsed by the time `start_season()` actually runs (e.g. configured during a long intermission) is rejected with a clear "pick a new one" error rather than silently freezing a bogus already-past `ends_at`.
  - `rename_season()` (owner-only, any status) sets `seasons.name`, capped at 60 characters; blank clears it back to the "Season N" display fallback. Purely cosmetic, no notification.
  - Seeding still happens in exactly the same two places as before: first-time join, and season start (now for the *default-included* population above, not a literal opt-in list).
- **`delete_group` / `cancel_group_deletion`** — an owner-initiated delete is immediate, not grace-period. `delete_group` (owner-only) voids+refunds every non-terminal market in the group right away (via the same `_void_market()` helper `end_season()` uses), then drops the group row in the same call — every group-scoped table cascades from `groups.id`, so a plain `DELETE` is enough, no manual cleanup and no separate sweep. There's no undo once it's called. `groups.deletion_scheduled_at` and `cancel_group_deletion` still exist, but purely for the *other*, unrelated thing that uses them: the same grace-period mechanism fires automatically — `group_deletion_scheduled_inactivity` instead of `group_deletion_scheduled`, honest distinct copy since nobody actively did anything — when a group sits in `intermission` for 30 days with nobody continuing, scheduling the row deletion 5 days out and blocking new markets/members in the meantime (`create_market`/`join_group` both check the column) so a member can see it coming and the owner has a real window to `cancel_group_deletion` or `start_season()` a new one (which clears the flag and emits the ordinary `group_deletion_canceled`, since that really is what canceled it) before `expire_stale()` sweeps up the actual `DELETE`. An owner clicking delete manually never touches `deletion_scheduled_at` at all — it's a completely separate code path that happens to still share `groups.deletion_scheduled_at`'s column and `cancel_group_deletion`'s undo, only for the inactivity trigger.
- **`react_to_market`** — one fixed emoji per person per market (`fire`/`laugh`/`clown`/`salute`/`thumbs_up`/`thumbs_down`), only ever on a `resolved`/`voided` market (gated by `is_market_visible()`, same choke point as everywhere else — a market's own subject can react too, once it resolves). Tapping the current pick again clears it; tapping a different one swaps it. No push notification. `lib/reactions.ts` holds the one canonical emoji/glyph mapping and display order, shared by the interactive picker (`ReactionBar`, on the reveal ticket) and a compact view-only facepile rendered on resolved/voided market rows/cards in the group hub — the latter shares its badge slot with the `needsAttention` "!" badge above, since a market can only ever be `open` (attention) or `resolved`/`voided` (reactions), never both.
- **Awards** (`group_titles`) — 8 persistent flavor badges (`lib/titles.ts`: The Oracle, Ice Cold, Bandwagon, Cursed, On Fire, Degenerate, Whale, Risk Taker) shown as flair next to a nickname (`<Mention titles={...}>`) everywhere, not just a leaderboard page. All 8 are computed from real (never `voided`) bet/ledger history, restricted to still-active memberships. 7 of them (`_recompute_group_titles`) are comparative rankings across the whole group and only recompute every 3rd market that resolves (`group_settings.markets_resolved_since_titles`, bumped by `_bump_titles_counter` from inside `finalize_market`) — recomputing on every single resolution would flip a title back and forth on a couple of noisy bets. Risk Taker (`_upsert_risk_taker`) is the exception: it's monotonic (only a genuine new all-time-best payout multiple ever changes the holder, the same stat the `impressive_bet` push already tracks), so it updates live on every resolution with no flapping to guard against, and replaced the old standalone "most impressive bet" leaderboard card. A vacant title (nobody yet qualifies, e.g. under the 5-settled-bet minimum) is still a row with `user_id = null`, so the UI can show "unclaimed" rather than not knowing whether it's ever been computed. The leaderboard page's "Accuracy" stat reuses The Oracle's exact win-rate definition (bet's side/option matches the market's real outcome, min. 5 settled bets on `status = 'resolved'` markets) but isn't a stored `group_titles` row — it's computed ad hoc for every qualifying member each time the page loads, since it's a full ranking display, not a single-holder badge.
- **`set_group_avatar`** — owner-only, sets/clears `groups.avatar_key`. 404s for a non-member before it ever checks ownership, same posture as every other group function.
- **`set_notifications_enabled` / `update_notification_categories` / `update_group_notification_prefs`** — the three writes behind `/profile/notifications` (see "Notification preferences" below). All three act on the caller's own row only, so there's nothing to authorize beyond membership.
- **`get_group_by_invite_code` / `_enforce_invite_code_rate_limit` / `_record_invite_code_miss`** — the invite-code preview a non-member gets on `/join/[code]` (group name, `accepting_members`, and the caller's own membership status, nothing about members, markets, or bets), plus the two internal helpers behind the 10-misses-per-hour guess limit it shares with `join_group`. Both helpers are revoked from `authenticated`; only those two functions call them. See "Guessing at invite codes is rate limited in the database" above for why the miss paths stopped raising and why the preview is VOLATILE.
- **`_notification_category` / `_prefs_allow`** — internal helpers mapping an event type to one of `markets`/`results`/`admin`/`nudges`/`promos`/`other`, and deciding whether a given recipient's preferences let that category through. Both revoked from `authenticated`; only `get_event_recipients` calls them.
- **`send_nudges()`** — the second cron entry point, every 15 minutes (`barbets-nudges`), deliberately *not* folded into `expire_stale()`: everything in that function is load-bearing (markets closing, votes finalizing, seasons archiving, groups deleting), and these two nudges are flavor, so a bad query here can't throw partway through and leave a season un-archived. It emits two events and decides only *whether there's anything worth notifying about* — never who, which is entirely `get_event_recipients`' job.
  - **`weekend_nudge`**: Friday 12:00-12:15 in the group's *own* `group_settings.timezone` (which until now was a pure display caption). Only for groups that could act on it (betting currently open, not in intermission, not scheduled for deletion, at least 2 active members) and only for **quiet** ones: nothing currently open, and nothing created in the last 3 days. A group already mid-conversation doesn't need prodding. Deduped to one per group per 5 days against `notification_events` itself, which also covers an owner changing the timezone mid-week. Group-scoped with no `market_id` (that's the point), so it joins the `notification_events_market_events_have_market` allow-list.
  - **`market_closing_soon`**: an `open` market inside 2 hours of `closes_at`. `markets.closing_nudge_sent_at` is stamped once so it can never fire twice for the same market (the same one-shot pattern as `closed_at`), and `distinct on (group_id)` plus a 24-hour lookback caps it at one per group per day, so a group closing four markets at once costs a lapsed member one push rather than four. That cap is per *group* rather than per recipient on purpose: the recipient set is the same lapsed-member set either way, which makes the cheap check the correct one and avoids a per-user delivery log.
- **`expire_stale()`** — the cron entry point, scheduled via pg_cron every minute (`barbets-expire-stale`, same cadence as send-push below — tightened from an original 5-minute interval once send-push proved 1-minute pg_cron scheduling works fine on this project's plan). Covers 24h (or closes_at) unsponsored expiry, market auto-close at `closes_at` (stamping `closed_at`) — **except for a market that reaches `closes_at` with literally zero bets ever placed, which gets voided outright via `_void_market()` instead of closing**, since there's nothing for anyone to propose/challenge/vote on and it would otherwise sit in `closed` forever waiting on a proposal nobody had a reason to make; that auto-void is deliberately silent (no `market_closed`, no `market_voided`), the same "nothing happened here" convention the unsponsored expiry already uses, and only the natural sweep is affected (a human calling `propose_resolution` on a zero-bet market is still a deliberate action and untouched) — no-challenge auto-finalize and vote-window auto-finalize (both against each group's own `resolution_window_hours`), the `winding_down` hard-cap sweep (force-void anything still `proposed`/`disputed` past `wind_down_deadline`, then archive), timed season auto-end (a plain `seasons.ends_at <= now()` check, not recomputed from `group_settings` — see above), the 30-day-abandoned-intermission sweep (schedules group deletion the same way `delete_group()` does), the grace-period group-deletion sweep, and the timed season auto-end. **Every loop body is wrapped in its own `begin ... exception ... end` block**, which in PL/pgSQL is an implicit savepoint: a raise on one row rolls back that iteration only and the loop continues. Before `20260813180000` there was no error handling at all, and since pg_cron's `select expire_stale();` is a single transaction over every group on the platform, one bad row rolled back the entire run and then did it again every minute forever — see "Notable design decisions." A failed iteration is recorded in `sweep_failures` instead (the write survives, since only the inner savepoint rolled back), and `send-push` posts one Slack card per stuck row. The row-locking loops use `for update skip locked` so a market a member is actively acting on is skipped this minute rather than blocking all nine sweeps for everyone. `get_cron_job_status()` (service_role only) reports every `barbets-*` job's registered schedule for debugging (there are four now: `barbets-expire-stale`, `barbets-send-push`, `barbets-nudges`, and `barbets-purge-notifications`), since `cron.job` isn't exposed via PostgREST directly.
- **`_end_season(p_group_id, p_actor_id)` / `end_season(p_group_id)`** — the season-ending work, and the authorization gate in front of it. They are separate because `end_season()` reads its caller from `auth.uid()` and requires them to be the group's owner, which means it could never be called by cron: `auth.uid()` is NULL there, so the membership check matched nothing and it raised `not_found`. `expire_stale()` had been calling it for every season past `ends_at` since `20260719147000`, so timed seasons never auto-ended *and* that raise aborted the whole platform's sweep. `_end_season()` takes its actor as a parameter (NULL from cron, which is exactly what `_finalize_season` already expects for a season nobody ended) and asks no authorization questions; `end_season()` is now nothing but the not_found/forbidden checks plus a delegation. Covered by `tests/integration/lifecycle.season_auto_end.test.ts`, which is the first test in the suite to use a non-`manual` season length — every other one leaves `ends_at` NULL and never reaches that loop, which is why this went unnoticed.
- **`purge_processed_notification_events()`** — the 30-day retention cleanup of already-`processed_at` `notification_events` rows (that table otherwise has no retention policy; nothing queries events by age, but there's no reason to keep them forever), plus `sweep_failures` rows untouched for 30 days. Its own daily cron entry (`barbets-purge-notifications`, 03:17 UTC) since `20260813180000`, having previously been folded into `expire_stale()` — see "Notable design decisions" for why that moved.
- **`group_members_who_played(p_group_id, p_membership_ids)`** — which of those memberships have any non-seed `ledger` entry, for the leaderboard's "does this departed member still belong on the board?" test. It exists because `ledger_select_own` is own-rows-only, so the page cannot answer that question about anyone but the viewer (see the design note). It is deliberately the *narrowest* function that answers it: **membership ids only, never an amount, a count, or a date**, gated on `_caller_is_active_group_member()`, and matching `m.group_id = p_group_id` per row so a caller can't probe membership ids belonging to another group. The one bit it discloses ("this person played") is already what their row on the leaderboard says out loud. A function returning someone else's *net* or weekly swing would be a different decision and this is not a precedent for it.
- **`_record_sweep_failure()` / `claim_unreported_sweep_failures()` / `get_sweep_failures()`** — the `sweep_failures` plumbing. `_record_sweep_failure` is called from inside `expire_stale()`'s exception handlers and upserts with an attempt counter rather than inserting, since a permanently stuck row is retried every minute and one row per minute would bury its own signal. `claim_unreported_sweep_failures` marks and returns in one statement, the same claim pattern as `claim_notification_events` and for the same reason. `get_sweep_failures()` is a service_role read-only diagnostic, same idea as `get_cron_job_status()`.

## Money & the ledger

`ledger` is an append-only, signed log (`seed` / `bet` / `payout` / `refund`) — no client can ever UPDATE or DELETE it. Every balance change writes a matching ledger row in the same transaction that changes `memberships.balance`, so the ledger is always independently reconstructable and auditable.

**"All-time net" is one figure with one definition, and it comes from a view, not a client-side sum.** Every ledger entry except the `seed` itself (so reseeding for a new season doesn't read as "winning" tokens back). `membership_ledger_net` (`20260813190000`) aggregates it in Postgres and is what the groups hub, `/profile`, and the leaderboard's all-time card all read:

```sql
create view membership_ledger_net with (security_invoker = true) as
  select m.id as membership_id, m.user_id, m.group_id,
         coalesce(sum(l.amount), 0)::bigint as net,
         count(l.id)::bigint as entry_count
  from memberships m
  left join ledger l on l.membership_id = m.id and l.reason <> 'seed'
  group by m.id, m.user_id, m.group_id;
```

`entry_count` distinguishes "no activity" from "activity that happens to net to zero", which a bare sum cannot. Note that it is subject to the same own-rows-only limit as `net` below, so it can only answer that question about the viewer themselves. **The cross-member version of the question goes through `group_members_who_played()`**, not through this view.

**The zero this view returns for other people is not their real net.** `ledger_select_own` is own-rows-only, and `security_invoker = true` means the aggregate runs under the caller's own RLS, so asking for another member's row yields `net = 0, entry_count = 0`. That is deliberate and matches what the client-side sums it replaced already produced, but it is a number that looks real and isn't. Anything that genuinely needs another member's net must go through a SECURITY DEFINER function and decide, explicitly, that exposing it is intended. See the design-decisions note for the two call sites currently living on that zero without meaning to.

## The market page template

`app/(app)/groups/[groupId]/markets/[marketId]/page.tsx` renders one of four screens off `markets.status`. Three of them share a single template with a **fixed section order**; the point of the fixed order is that a member who has learned one market type has learned all of them, so nothing moves when the type changes.

Shared chrome on every one: the back link carries the *group's* name, the status pill and the `···` overflow (owner void, or the creator fallback when the owner is a subject) sit beside it, and a dark `PoolStrip` sits under the title. Three cells everywhere, with exactly one exception: an **open market carrying a `bonus_pool` takes a fourth Bonus cell** (`Pool / Bonus / Bets / Closes`, per-cell `flex` weights, a `bg-honey-500/12` wash behind Bonus, and the third label shortened from "Closes in" to "Closes" to fit). The over/under line still never gets a cell — it lives in `LineTicket`. See the design-decisions note below for why the bonus reversed and the line didn't.

A cell whose figure is tappable passes a client component as its `value` (`ClosesInValue` → the exact close time, `BonusPoolValue` → the bonus explainer) rather than an `onPress` handler, which is what keeps `PoolStrip` itself renderable from a server component. Both use the same affordance on the dark strip: `underline decoration-dotted decoration-espresso-300`.

| status | screen | strip cells | the one action |
|---|---|---|---|
| `pending_sponsor` | endorsement | Endorse by / Betting runs / Table | pinned "Endorse it" + "Not now" bar |
| `open` | the five-slot template | Pool / Bets / Closes in, or Pool / Bonus / Bets / Closes with a `bonus_pool` | pinned bet slip |
| `proposed` | the proposed call | Pool / Bets / Final in | "Challenge this call", in slot 4 |
| `closed` | waiting on a result | Pool / Bets / Status | "Propose the outcome", in slot 4 |
| `disputed` | the secret ballot | Pool / Bets / Vote ends | the ballot itself |

Every stage's action goes through `ResolutionTimeline`'s `children`, including on `closed` — `ProposeResolutionCard` has no card, copy, or divider of its own and only varies its label ("Propose result early" while betting is still open, since proposing is what closes it; "Propose the outcome" once it already has). It used to render its own dashed "waiting on a result" card above the timeline, which put the button in a different place on `closed` than on `open` and restated what the timeline's first step already said.

The five slots, in order: **(1)** your position (`PositionTicket`), only when you have money down; **(2)** otherwise the explainer — `LineTicket` for over/under, `OptionsTicket` for multiple choice, and *nothing* for yes/no, where the question is already the explanation; **(3)** `HowItSettlesCard`, criteria plus the started-by/endorsed-by/hidden-from chips, with `ClarificationRequests`' "?" in its corner; **(4)** `ResolutionTimeline`, whose `children` are the stage's one action under a divider; **(5)** `BetslipBar`, pinned above `BottomNav`, the only place a stake is ever entered.

`TicketCard` is the outlined shell slots 1 and 2 share with the endorsement screen's `VouchingTicket` and the proposed screen's `ProposedOutcomeTicket`. Exactly one of them is ever on screen at a time — that is what makes the heavier outline mean "this is the thing you're deciding about" rather than being decoration. On `proposed` that means the viewer's own position renders *inside* `ProposedOutcomeTicket` rather than in a ticket below it (`PositionRows` is shared by both): what a call is worth to you is not a separate fact from the call, it's the first thing anyone reads it for, and two cards made you look in two places to answer one question.

Two decisions here are load-bearing enough to have their own entries in "Notable design decisions": why slots 1 and 2 exclude each other and why the stage's action never sits where betting does, and why the drawn payout projection was dropped rather than built (short version: it would have repealed sealed odds).

**Banded modals.** Four modals own their own edge-to-edge header/footer bands instead of `Modal`'s default padded stack: the bonus pool explainer (`BonusPoolValue`), its group-level twin (`PendingBonusPoolNote`, same band and the same two-row arithmetic block for money that has no market yet), "Call the result" (`ProposeResolutionCard`, two steps under one band that reads `Step 1 of 2` / `Step 2 of 2`), and owner void (`MarketOverflowMenu`'s `VoidAction`, also two steps under one band). They share the band styling with `TicketCard` on purpose — `bg-espresso-50 px-[18px]`, uppercase label left, meta right — so a modal reads as the same object family as the cards behind it. `Modal` takes `padded={false}` plus a `panelClassName` for this rather than being forked; every other modal in the app still gets the default `space-y-3 p-5`.

"Review your market" uses the same band and the same espresso outline but is **no longer a modal** — it's step 3 of the create-market wizard (`ReviewTicket` in `MarketForms.tsx`), a full page like the two steps before it. It is still where the endorsement rule lives (it used to be small print under the create form's submit button, explaining the consequence of an action nobody had taken yet), and it still only appears when `group_settings.require_endorsement` is actually on, since "betting opens as soon as you create it" is the unremarkable default and doesn't need a highlighted callout.

Two of them (`ProposeResolutionCard`, `VoidAction`) list the consequences of confirming as `ConsequenceRow` (`components/ui/ConsequenceRow.tsx`): coloured dots strung on the same connecting rail `ResolutionTimeline` draws, because these are steps in order, not bullets. The dot colour ranks them — danger for what happens to other people immediately, dark for the window they get to react in, faint for the eventual end.

**After a bet lands**, `BetslipBar`'s `BetConfirmedOverlay` takes the whole screen: a torn ticket stub carrying stake, side, market title, group, a live `CountdownTimer`, and the balance left. It still shows no odds or projected payout, same rule as the slip itself. Its one button goes to the group's market list, not back to this market — the bet is placed and the odds stay sealed, so there is nothing left on the market page to come back for.

## Server Actions & error handling

Every mutating action in `lib/actions/*.ts` calls a Postgres RPC and returns an `ActionResult<T>`:

```ts
type ActionResult<T> = { data: T; error?: undefined } | { data?: undefined; error: string };
```

**This is load-bearing, not a style choice.** Next.js redacts any error *thrown* out of a Server Action in production — the client only ever sees a generic message + a digest, never the real text, even for an expected rejection like "betting is not open on this market." Actions must catch the Postgres error and *return* it instead; client components check `result.error` rather than wrapping the call in try/catch. `lib/errors.ts`'s `runRpc()` does this conversion and also strips the internal `invalid_operation:` / `not_found:` style prefix so the user sees plain text, not what looks like an error code.

Read-only Server Components query `visible_markets` and read-only RPCs directly — those still throw/404 via `notFoundIfEmpty()`, since that path isn't subject to the same Server Action redaction.

There is exactly one **read-only Server Action**, `loadMoreSettledMarkets()` in `lib/actions/feed.ts`, behind the group feed's "Load more" button. It calls no RPC, but it still returns an `ActionResult<T>` for the reason above: the redaction rule is about *how a Server Action fails*, not about whether it mutates, and the button needs copy it can actually render. It does no membership check of its own — `visible_markets` is the choke point, and a caller who isn't in the group gets an empty page, indistinguishable from having reached the end of the list.

## Notifications

`notification_events` is an internal queue table (no RLS policies at all — only `service_role` touches it) written transactionally by whichever Postgres function causes a notifiable transition. This is deliberate: several transitions (market auto-close, auto-finalize, auto-end-season) only ever happen via the `expire_stale()` cron job, so hooking notifications into Next.js Server Actions would silently miss most of them. Writing the event *inside* the same Postgres transaction that changed the state means "this happened, exactly once" is transactionally safe, decoupled from "send a push" (network I/O, retryable).

`get_event_recipients(event_id)` is the single choke point for who gets notified: it reuses the same subject-exclusion logic as `is_market_visible`, filters to members with a live `push_subscriptions` row and `notifications_enabled = true`, applies the recipient's own per-category/per-group preferences via `_prefs_allow` (see "Notification preferences" below), and excludes the triggering actor (`actor_id`) if there is one. Notably, `finalize_market()`'s actor is just `auth.uid()` — when a voter's ballot auto-finalizes the market in the same request, that's still their session, so they're correctly excluded from the "market resolved" push about their own action; cron-triggered finalizes have no request context, so `auth.uid()` is null and nobody is excluded on that basis. `betting_opened` and `season_ended` are group-scoped (every non-removed member, actor excluded) rather than market-scoped. `impressive_bet` repurposes `actor_id` to mean the opposite of everywhere else: the one person to notify, not the one to exclude — `finalize_market()` sets it to the bettor whose payout just became the group's new all-time-best payout multiple (`payout ÷ amount`, see `get_most_impressive_bet()`), and only they get the push. `member_joined` is also group-scoped but single-recipient like `impressive_bet` — its one recipient is always `groups.owner_id`, not the actor, so a group with a large roster doesn't get a push blast every time someone joins; only `join_group()`'s genuinely-new-membership paths emit it, not a dormant member's rejoin. `market_voided` is market-scoped like `market_resolved` and joins it in the subject-inclusion branch (`p_include_subjects`) for the same reason: voiding lifts `is_market_visible()`'s privacy gate just like resolving does, so subjects are very much part of the intended audience, not excluded from it.

`claim_notification_events(p_limit)` is how a run takes work off the queue. It marks the oldest `p_limit` unprocessed rows processed and returns them in one statement, using `for update skip locked` so a second run gets a disjoint slice rather than blocking. This is the thing that makes the batch size a throughput decision instead of a gamble: the old shape selected unprocessed rows and wrote `processed_at` only after sending, which is safe exactly as long as a run finishes inside its own cron minute, and re-sends the whole batch to everyone the moment one doesn't. It is deliberately at-most-once (see "Notable design decisions"). The batch size is applied as `limit coalesce(p_limit, 200)`, not `limit p_limit` against a parameter default, for the reason in "Notable design decisions" below.

A scheduled Supabase Edge Function (`supabase/functions/send-push`, Deno, run every minute via pg_cron + pg_net) claims up to 200 events per run, computes recipients, and sends real push notifications over two channels depending on `push_subscriptions.platform`: `web-push` for browser/PWA subscribers (`endpoint`/`p256dh`/`auth_key`), and Firebase Cloud Messaging for the Capacitor native app (`fcm_token`) — one `push_subscriptions` row per device either way, `platform in ('web', 'android', 'ios')` with a same-table shape CHECK enforcing exactly one credential set per row (`20260722100000_native_push_tokens.sql`). FCM's HTTP v1 API needs a Google OAuth2 access token, not a static key, so `send-push` mints one itself from the `FCM_SERVICE_ACCOUNT_JSON_B64` secret via a self-signed JWT using Deno's native Web Crypto (`crypto.subtle`) — no JWT library needed for one call. Both channels send the same `{ title, body, url }` shape; a tap lands on the same target either way, via `sw.js`'s `notificationclick` handler on web or `components/pwa/NativePushNavigation.tsx`'s `notificationActionPerformed` listener natively. Dead subscriptions (404/410 from the push service, or `UNREGISTERED`/`NOT_FOUND` from FCM) are cleaned up automatically. `FCM_SERVICE_ACCOUNT_JSON_B64` is optional — a project that hasn't set up Firebase yet just skips native sends instead of failing the whole event. Stored base64-encoded rather than as raw JSON, and its parse is wrapped in try/catch even though it's top-level module code: a Google service account key is nothing but double quotes and embedded newlines, exactly what shell argument quoting mangles first when running `supabase secrets set`, and this bit the project for real once already — a malformed secret crashed the function's module initialization outright, taking down *all* push (web included) since a module that throws before `Deno.serve()` never serves a single request, not just the FCM path.

Inside a run the work is split into deciding and sending, and that split is the whole reason the throughput ceiling moved. `eventDeliveries()` resolves an event's recipients and copy into a list of `{ userId, content }` without sending anything, and those run over the claimed batch with a small concurrency (`EVENT_BUILD_CONCURRENCY`, database reads only). `deliverAll()` then looks up subscriptions for the entire batch in chunks of 100 user ids — chunked because supabase-js sends selects as GET, so an `in.(...)` list of UUIDs becomes URL text — and runs every resulting push through one pool of `SEND_CONCURRENCY` (20). The previous shape did a subscriptions query per recipient and awaited each send in turn inside two nested loops, so a 40-person event cost 40 round trips before the first notification left the building. A per-run promise cache (`lookup()`) memoizes the small repeated reads (`groupRow`, `marketAndGroup`, `resolutionWindowLabel`), which matters because a batch is usually several events from the same group; it is reset per run so a warm isolate can't serve a stale group name after a rename. **Events is the wrong unit for capacity** — one `admin_broadcast` to a 40-person group is a single event and 40-odd sends — so `SEND_CONCURRENCY`, not `EVENT_BATCH_LIMIT`, is the knob that governs how fast a run drains.

"Resolved" is the one event whose copy varies per recipient, not just per subject/non-subject: `send-push` computes each recipient's own settled winnings on that market (summed across any bets, in case of a hedge) and quotes it directly for a winner, falling back to a shared "here's what happened" copy for everyone else with a non-zero result cached by that shared key, so a large group's blast doesn't rebuild identical content once per recipient. It also sums each recipient's **stake**, because `payout == stake` is a meaningfully different outcome from a real win: it can only happen on a one-sided market (`total_pool == winning_pool`, so the parimutuel formula returns the stake exactly, dust included), where there were no losing stakes to split. Quoting that as "you won N tokens" overstates it, and framing it as winning your own bet back reads like a consolation prize when the call was in fact right, so that case gets its own copy. The reveal page's ledger makes the same distinction: "Won / N returned" instead of "+0 won".

**`group_deletion_scheduled` (distinct from the still-live `_inactivity` variant above) is dead code, not a live event.** Now that an owner-initiated `delete_group` is immediate (see below), nothing emits it anymore — `send-push`'s `buildContent` still has a case for it, and the enum value still exists, but no function ever writes that event type into `notification_events`, so the handler can never actually run. Left in place rather than ripped out purely because it wasn't worth a bigger cleanup for dead code that costs nothing sitting idle; don't be misled into thinking a manual delete still pushes this.

**"Market opened about you" is the one deliberate crack in `is_market_visible()`'s otherwise-total pre-resolution wall.** Every other subject-facing surface (the market page, the group feed, every RPC) treats "subject + not yet resolved" as 404 — this event exists anyway because knowing *that* a market about you exists, with genuinely zero content, was judged worth breaking that wall for; nothing else was. `create_market()` (its direct-`open` path) and `sponsor_market()` both emit it alongside their existing `market_opened`, but only when the market actually has subjects, and `get_event_recipients` gives it the mirror image of every other market-scoped branch: subjects *only*, straight off `market_subjects` rather than `get_notification_recipients()` at all (every other branch does the opposite — excludes subjects by default). The push body never touches `market.title` — `buildContent`'s `market_opened_about_you` case is the one market-scoped switch arm that ignores the `market`/`group` values it's handed for exactly that reason. It deep-links to the same `/groups/{groupId}/markets/{marketId}` URL a `market_opened` push would use for anyone else; the market page itself decides what to render, not the push. `get_subject_market_pulse(_sides)` are two new SECURITY DEFINER functions, deliberately *not* built on `is_market_visible()` (that function's entire purpose is to say no here) — each does its own explicit check (real member of the group, an actual subject of *this* market, not yet `resolved`/`voided`) and hands back only: `status`/`market_type`/`closes_at`, total `bet_count`/`pool_amount`, and — for `yes_no`/`over_under` only — the odds split by side (`_sides` raises rather than returning a breakdown for `multiple_choice`, since option labels are exactly the kind of content this exists to hide). The market page tries `visible_markets` first as always; only when that comes back empty does it fall back to `get_subject_market_pulse`, rendering `SubjectMarketPulse` (no title, no description, no creator/subject list, no betting UI) instead of `notFoundIfEmpty`'s 404 if that succeeds too — anyone it's not actually meant for (wrong group, not a subject, market doesn't exist) still gets the same indistinguishable 404 as before, since the RPC raises `not_found` for all of those identically. Odds are shown even while the market is still `open`, unlike `get_closed_odds`' closed-only gate for everyone else — that gate exists to stop a bettor from being swayed by live odds while they can still act on them, which can't apply to a subject, since `is_market_visible()` already blocks `place_bet` for them same as everything else.

Reactions (`react_to_market`) are deliberately push-free — a resolved market's reveal ticket is a low-stakes, browse-when-you-feel-like-it surface, not something worth interrupting anyone for.

### Notification preferences

`users.notifications_enabled` is still the master kill switch, but it is no longer the only control. Preferences are split into the three different *reasons* a push arrives, not into a taxonomy of event types:

| Category | Where it's stored | What it covers |
|---|---|---|
| general (per group) | `memberships.notify_group` + `notify_markets` / `notify_results` / `notify_admin` | something happened in a group you're in |
| nudges | `users.notify_nudges` | nothing happened, and that's the point |
| promos | `users.notify_promos` | the app itself is talking to you (`admin_broadcast`, the only channel that exists to market at someone) |

**The page is one master switch over a per-group accordion.** `NotificationPreferences`'s first card, "All notifications", *is* this device's push subscription (`usePushSubscription`'s subscribe/unsubscribe, which also writes `users.notifications_enabled`) — it is not a fourth category. It reads as a master because it is one: nothing below it can arrive if it's off. The platform cases push can't serve (unsupported browser, iOS before install, permission already refused) replace that row's subtitle and disable its switch rather than swapping in a differently-shaped card, so the page never changes structure based on the device it's opened on. Below it, each group is one row carrying its master `notify_group` switch plus a one-line summary of which categories are on ("Markets and results on", "Results only", "Muted"); tapping the row expands the three category switches. The sub-switches stay mounted but dimmed and inert when the group is muted, because they're the answer to "what would I get back if I turned this on again" — unmounting them makes the master look like it deleted them.

**The general category lives on `memberships`, not in a new preferences table.** Identity in this app is already per-group (`memberships.nickname`), a membership row already exists for exactly the (user, group) pairs that can receive a group notification, and `get_event_recipients` already joins that table in every branch. A separate table would have needed its own RLS, its own lifecycle on join/leave/rejoin, and a left join with a default at every read.

**Nudges and promos are global rather than per-group on purpose.** "Stop pestering me" and "no marketing" are feelings about the app, not about one friend group, and making them per-group would mean re-answering them for every group you join. `_prefs_allow` still gates nudges on the per-group `notify_group` switch (a nudge is about one specific group, so muting that group mutes its nudges), while promos deliberately ignore it (they aren't really about the group they happen to be addressed through).

`_notification_category` maps every event type to one of these, and an **unmapped type falls through to `other`, which `_prefs_allow` lets through**. That's the deliberate failure mode: a new event type someone forgot to categorize gets delivered rather than silently dropped.

**`set_notifications_enabled()` exists because the old code path silently did nothing.** `setNotificationsEnabled()` used to do a plain `supabase.from('users').update(...)` from a Server Action, but `users` has select and insert policies and deliberately no update policy — an RLS-filtered UPDATE matches zero rows and reports success rather than erroring, so the master toggle had been a no-op. Routing it through a SECURITY DEFINER function is both the fix and what this codebase's "all mutation goes through SECURITY DEFINER functions" rule required in the first place. Worth remembering as a general trap: **a blocked UPDATE through PostgREST is indistinguishable from a successful one that matched nothing.**

## Platform admin, feedback, and access gates

**`app_admins` is the app's second authority model, and the only one that isn't per-group.** Everywhere else in this codebase, "can you do this?" resolves to `groups.owner_id` or to membership in a specific group; `app_admins` (one column, `user_id`) is platform-wide, and `is_platform_admin(p_user_id default auth.uid())` is the single choke point every admin-gated function and page calls first. The table is zero-policy (see the data model above) — nothing reads it directly, only that function does. `/admin` follows the same 404-not-403 rule as everything else: a non-admin doesn't get "you don't have permission," they get `notFound()`, so the page's existence isn't even confirmed.

The admin surface is deliberately small: `get_platform_admin_stats()` (active groups / total markets / total users), `list_groups_for_admin()` / `list_group_members_for_admin()` (the broadcast form's pickers), and `send_admin_broadcast(p_group_id, p_title, p_body, p_target_user_id default null)`. All go through SECURITY DEFINER functions rather than the service-role client (`lib/supabase/admin.ts`), which stays reserved for the two things genuinely impossible in SQL: bypassing Storage on the `resolution-proofs` bucket, and deleting an `auth.users` row. A platform-wide aggregate count is ordinary data access that just needs gating, which is exactly what SECURITY DEFINER is for.

**`admin_broadcast` is the one notification event with author-supplied copy.** It exists to test marketing/ad creative on real devices, and reuses the existing `notification_events` → `send-push` pipeline rather than opening a second delivery path, because the VAPID/FCM secrets are Edge-Function-only and unreachable from Next.js. It carries `custom_title`/`custom_body` (bypassing `_emit_notification_event()`, whose signature has no room for them and which 8 other call sites depend on) plus `target_user_id`, the only event type that has one. In `get_event_recipients` it gets its own branch rather than joining the shared group-scoped list, for two reasons: it can address one specific member instead of the whole group, and when it's targeted it deliberately **skips the usual actor exclusion** — an admin targeting themselves to check their own device should actually receive it, unlike an accidental self-broadcast.

**Feedback is stored in Postgres and delivered to Slack, in that order.** `submit_feedback()` (the only way into the zero-policy `feedback` table) writes the durable row — message, `category` (`bug`/`idea`/`general`), `wants_followup`, `page_url`, and a `group_id` that `lib/actions/feedback.ts` extracts from the referring URL when the submitter happened to be on a group page. Only *then* does the action post a Slack Block Kit card via `SLACK_FEEDBACK_WEBHOOK_URL`, best-effort inside a try/catch: the feedback is already durably saved by that point, so a Slack outage must never fail the submission. This posts directly rather than routing through `notification_events`, because unlike VAPID/FCM there's no secret here that Next.js can't hold.

**Production errors are tracked by posting them to Slack, with no third-party service.** `lib/errorReporter.ts`'s `reportError()` is the one place an unexpected throw becomes a Block Kit card on `SLACK_ERROR_WEBHOOK_URL` (a second Incoming Webhook on the same Slack app the feedback form already uses, pointed at a different channel). Three feeds reach it:

- **`instrumentation.ts`'s `onRequestError`** — Next.js's own hook, called for every error thrown out of server rendering, a Server Action, a route handler, or the proxy, including the ones the user only ever sees as a redacted digest. One hook instead of a try/catch in each of the ~40 places that could throw.
- **`app/global-error.tsx`** (new, and also the app's first global error boundary at all) — a client render crash never reaches the server on its own, and in an installed PWA that is most of what a user experiences as "the app broke". It posts back through the `reportClientError()` Server Action (`lib/actions/errorReport.ts`). It **skips reporting when `error.digest` is set**, since a digest means the error came from the server and `onRequestError` already sent it with a real un-minified stack.
- **`supabase/functions/send-push`** — its own ~30-line copy of the same idea (an Edge Function shares no code with the app bundle, and this file already prefers a few lines over a dependency). It runs on a cron with nobody reading its logs, so a broken push run used to be silent in both senses. Set the same webhook as a Supabase secret to turn it on: `npx supabase secrets set SLACK_ERROR_WEBHOOK_URL=...`. It also reports **`expire_stale()`'s** failures, via `claim_unreported_sweep_failures()` after the pushes go out: nothing in Postgres can post to Slack, and this function already runs every minute and already holds the webhook. Claiming marks rows reported in the same statement that returns them, so a row failing every minute produces one card rather than 1,440 a day. `_record_sweep_failure` then re-arms the flag on the 10th and 100th attempt and every 1000th after that (roughly 10 minutes, 1.5 hours, then every 17 hours at one attempt a minute), so a genuinely stuck row nags occasionally instead of resting entirely on someone having caught the first card. Counted in attempts rather than elapsed time, since attempts is what measures how stuck a row actually is: something that fails once and then succeeds never escalates. It deliberately doesn't claim when no webhook is configured — marking a failure reported with nowhere to report it would throw away the only signal.

**Every card carries plain-English triage, not just a stack trace.** A stack answers "what threw" but not the two things you need when the phone buzzes: is this bad, and what do I do now. `TRIAGE` in `lib/errorReporter.ts` matches nine failure shapes this stack actually produces (duplicate Postgres function overload, missing table/column, empty-value dereference, renamed export, hydration mismatch, network blip, statement timeout, session/JWT, and a still-useful fallback) and attaches a *What's happening* and a *What to do* section, each with one concrete first move: `npx supabase db push` for the migration-didn't-ship case, "check status.supabase.com before changing code" for a network blip, "paste this card into Claude Code" otherwise. A footer restates on every card that no balance can be affected, since every money change is a single transactional Postgres function call. `send-push` carries its own four-case version tuned to what breaks there (including the base64 FCM secret, which has bitten this project for real). When adding a case, match on something specific enough not to swallow unrelated errors and keep the fix to one action.

**Both reporters check the Slack response.** A malformed Block Kit payload comes back as a 400 with a body naming the offending block, *not* as a failed request — so an unchecked `fetch` would mean an empty channel and no trace of why. Non-2xx is logged with its status and body. Silent silence is the one failure mode error reporting cannot afford.

Why not Sentry or similar: the deliverable is "a Slack message when something breaks," and that is an HTTP POST to a URL this app already knows how to make. A hosted tracker would add a runtime dependency, a build step, a vendor account, and a paid plan for the Slack integration itself, to deliver the same message to the same channel. What a tracker really sells is grouping, rate limiting, and retention — the first two are cheap here (a fingerprint of `source|route|name|message|first stack frame`, capped at 3 reports per fingerprint and 30 overall per 10-minute window, per instance) and the third is what the Slack channel is. If the volume ever outgrows a channel, `reportError()` is the single seam to swap.

Two filters keep the channel honest, and both matter more here than in a typical app: **Next's control-flow throws** (`NEXT_NOT_FOUND`, `NEXT_REDIRECT`, ...) are skipped, because the 404-never-403 rule means `notFound()` is thrown on every hidden-market read and is completely routine; and **an `ActionError` with a known business-rule code** (`not_found`/`forbidden`/`invalid_operation`/`insufficient_balance`) is skipped, because those are the database saying no on purpose. Only an `unknown` code is a real fault. The check is duck-typed on `.code` rather than `instanceof ActionError`, since `instrumentation.ts` is its own module graph. Note that Server Actions barely feature here by design: they *return* business-rule errors rather than throwing them, so anything that does throw out of one is genuinely unexpected. Reporting is gated to `VERCEL_ENV === 'production'` (falling back to `NODE_ENV` when there's no `VERCEL_ENV`), because preview deploys also run with `NODE_ENV=production` and would otherwise page you for every branch. `console.error` still fires in every environment regardless — the console is the record that always exists, Slack is the one that pages you.

**"Waiting on you" tasks (`lib/tasks.ts`) partially walk back the Inbox deletion.** `getGroupTasks()` returns the two market states genuinely blocked on one specific viewer — endorse a `pending_sponsor` market they didn't create, vote on a `disputed` market where they're neither a hidden subject nor already a voter — mirroring `sponsor_market`/`cast_vote`'s own eligibility exactly, so the UI never offers a task the RPC would reject. It feeds three surfaces: the group hub's `WaitingOnYouCard` (full list), the all-groups page's per-row count, and a red dot on BottomNav's Home tab (batched via `getGroupTaskCounts()`). This is the count and list only, **not** a re-homed Inbox page — see the BottomNav design-decision note below for what was deleted and why this much came back. `WaitingOnYouCard`'s dismissal is keyed to a *signature* of the current task set rather than a plain seen/unseen flag, so a new task automatically un-dismisses the card instead of it staying hidden forever after one dismiss.

**The beta gate is a single flag, currently off.** `lib/betaGate.ts` exports `BETA_GATE_ENABLED` (`false` today), a shared code, and a cookie name; when on, `proxy.ts` bounces an uncookied `/login` to `/under-construction`, and `checkBetaCode()` sets a 30-day httpOnly cookie on a correct code. It's built to be deleted — turning the flag off is enough, and nothing else in the app depends on it. Its `safeNext()` only ever redirects to a relative in-app path, never an absolute URL from form input; `app/auth/confirm/route.ts` applies the identical guard to its own `next` param.

**Password recovery uses `verifyOtp`, not PKCE code exchange.** Supabase's Reset Password email template is customized to point at `/auth/confirm` with `token_hash`/`type`/`next` instead of the default `{{ .ConfirmationURL }}`; that route establishes a real session from the recovery token and hands off to `/reset-password` to actually set the new password. If recovery emails ever stop working, check that template first — the flow depends on it not being reverted to the default.

## PWA & push

- `public/manifest.json`: `start_url`/`scope` are both `"/"` (not a page that requires auth — Android's install criteria need a reachable start URL), standard + maskable icons.
- Maskable icons must be a full-bleed square with a *solid* background (no transparency, no pre-baked rounded corners) — Android applies its own mask shape at display time, and content needs to sit within the inner ~80% "safe zone." A rounded, padded source image shows up with blank corners once Android's own mask is applied over it.
- The Android push **badge** (small status-bar icon) is a *separate*, dedicated asset (`badge-mono.png`) — Android renders it as a solid-tint silhouette using only the alpha channel, ignoring color entirely. The regular full-color app icon is used for the larger in-notification `icon` field, which platforms that support it still show in color.
- `public/sw.js`: network-first for everything (this app is almost entirely dynamic — a stale cached market page could show wrong odds), with a resilient `Promise.allSettled` app-shell precache so one failed asset can't block install. Bump `CACHE_NAME` whenever `SHELL_URLS` changes.
- **Offline (web/PWA)**: a failed navigation (`event.request.mode === 'navigate'`) falls back to the precached `/offline` page (`app/offline/page.tsx`) instead of a stale snapshot of `/` — that used to be the fallback, and for a logged-in visitor a cached copy of the logged-out marketing page read as a broken app, not "you're offline." `/offline` has to render correctly from the exact HTML precached at install time, so it does no server data fetching, no auth check, and no `next/image` (its optimization endpoint is a network request the service worker hasn't cached, so it'd render as a broken image offline) — a plain `<img>` against an already-precached asset instead, same reasoning `RevealTicket.tsx` uses. It also shows a read-only "last known balances" list, sourced from `lib/offlineSnapshot.ts`'s localStorage snapshot (one `{groupId, groupName, balance, savedAt}` row per group, written by `SaveBalanceSnapshot` whenever the group hub page loads) — the one piece of app data cached client-side, deliberately never odds or bet state, and always labeled "may be out of date." This only ever helps once the service worker has actually installed from a prior online visit; there's no fallback for a cold load that's offline from the very first visit.
- **Offline (native/Capacitor)**: the web fallback above doesn't reach the native shell — Android's WebView doesn't support service-worker interception of the top-level navigation request at all (only sub-resource requests), so a cold app-open with no connection never reaches the service worker and instead shows the WebView's own generic connection-error screen. `capacitor.config.ts`'s `server.errorPath: 'offline.html'` is Capacitor's own native hook for this (`BridgeWebViewClient.onReceivedError`/`onReceivedHttpError` on Android, `didFailProvisionalNavigation` on iOS): it loads a page bundled locally from `webDir` with zero network. `public/offline.html` is that page — fully self-contained (inline CSS, no React/Next.js/next/font, since none of that build output is available to a natively-bundled static file), synced into both native projects via `npx cap sync`. This needs a real native build/store release to reach users, unlike everything else in this section, which a web deploy alone covers.
- **The native shells run current JS against a plugin layer that can be months old, and that asymmetry breaks things in one specific way.** `capacitor.config.ts` sets `server.url` to the deployed app, so a Vercel deploy reaches every install immediately — the web layer is never stale. The *plugin* layer only moves when someone ships a store build. So **any web release that reaches for a newly-added Capacitor plugin runs against installs that don't have it**, and the bridge answers with an `UNIMPLEMENTED` rejection rather than the plugin's real result. This has already happened once: the day `@capacitor/share`/`@capacitor/filesystem` were added for image sharing, every existing Android install started running the new share code against a shell with neither plugin, and the button just read "Try again". `lib/shareImage.ts`'s `isMissingPlugin()` translates that class of rejection into "Update the app from the store" instead of surfacing `"Share" plugin is not implemented on android`. **Adding a plugin is a store release, not a deploy** — and until that release lands, the feature needs a graceful answer for the installs that don't have it yet.
- iOS never fires `beforeinstallprompt`. `usePushSubscription`'s `platform === 'ios-needs-install'` detects iOS + not-yet-installed, and the "All notifications" master row locks its switch and says to install to the home screen first rather than firing a permission prompt that can't work; this triggers automatically, nothing to configure.
- The "All notifications" master row at the top of `NotificationPreferences` (on `/profile/notifications`, its single mount point, above the preferences it gates) and `components/pwa/InstallPrompt.tsx` (on `/profile/account`) are the durable place to opt in/out or find install instructions again, but a brand-new user has no reason to visit a settings page — `components/pwa/InstallBanner.tsx` (dismissible, `localStorage`-remembered) and `components/pwa/PushReminderModal.tsx` are both mounted app-wide in `app/(app)/layout.tsx`, not on any one page, so they're visible regardless of which page a member happens to land on first (group hub, groups list, profile, ...). `InstallBanner` carries its own `mx-auto max-w-lg px-5` sizing internally rather than the layout wrapping it in one, so it contributes zero layout on the (common) pages where it renders null. `useInstallPrompt.ts` holds the platform/`beforeinstallprompt` detection shared by `InstallPrompt` and `InstallBanner`.
- `PushReminderModal` used to exist, get removed for being an app-wide interrupt, then get reinstated — the actual complaint wasn't "it's a modal," it's that it opened and then immediately closed itself for anyone already subscribed: `platform` flips to `'ready'` synchronously on mount while the real subscribed/not-subscribed answer is still an in-flight promise, so any consumer gating on `platform` alone reads the still-default `subscribed === false` for one tick. `usePushSubscription`'s `subscribedKnown` flag exists solely so a consumer can wait for that promise instead of the synchronous placeholder. It's also gated on `useInstallPrompt`'s `platform === 'installed'`, not just push-API support — Chrome (desktop or Android) will grant Web Push permission from an ordinary browser tab with nothing installed, but asking before install stacks this modal's full-viewport overlay directly on top of `InstallBanner` on the group page and visually hides it; deferring until installed also means `InstallBanner`'s job is already done by the time this fires, so its copy doesn't need an iOS-specific "install first" branch the way the old version did. The modal opens right after joining/creating a group (`JUST_JOINED_GROUP_KEY` in `localStorage`, set by `JoinFlow`/`CreateGroupForm` immediately before their redirect so it survives the navigation — relevant once already installed, e.g. joining a second group from the installed app) and otherwise at most once every `REPROMPT_DAYS` (7) on an ordinary app open — never for a `permission === 'denied'` device, since `requestPermission()` there just instantly re-returns `'denied'` with nothing the user can do about it from inside the app.
- VAPID private key lives only as a Supabase Edge Function secret, never in Next.js env or the client bundle. Same posture for the FCM service account key (`FCM_SERVICE_ACCOUNT_JSON_B64`, Capacitor/native push) — a Supabase secret only, never shipped client-side.
- **A service worker registration outlives the site that created it, and a 404 does not clean it up.** This matters because `mybarbets.com` served this app (and therefore registered this `sw.js`, cache `barbets-shell-v7`) before becoming the marketing site. Per the spec's Update algorithm a non-ok script response rejects the update job and only removes the registration when nothing is installed — the proposal to make 404/410 unregister was closed wontfix (w3c/ServiceWorker#204). Serving nothing at `/sw.js` would therefore leave the old worker controlling that origin indefinitely, still firing app push notifications whose relative `data.url` values 404 there. So `barbets-www` serves a deliberate *farewell* worker at that path instead: it wipes all caches, has **no `fetch` handler at all** (a registration without one cannot intercept navigations, so it provably cannot shadow the marketing pages), discards any push payload and shows one `tag`-collapsed "Barbets has moved" notification, and unregisters itself plus its push subscription on a date baked into the file. That last part also cleans up the stale rows for free: the dead endpoint starts returning 404/410, and `send-push` already deletes on those. Nothing on the marketing site ever calls `navigator.serviceWorker.register()`, so no new visitor gets a worker.
- Inside the Capacitor shell, `usePushSubscription.ts` branches on `Capacitor.isNativePlatform()` to a completely different registration path (`@capacitor-firebase/messaging`'s `requestPermissions()`/`getToken()` instead of the Web Push API) rather than trying to make one code path cover both — the two have almost nothing in common (permission model, subscription object shape, how you detect an existing subscription on mount). Both still funnel into the same `push_subscriptions` table and the same `setNotificationsEnabled()` toggle, so the "All notifications" switch doesn't need to know which path is live.

## Testing

`npm test` runs Vitest integration tests directly against a real hosted Supabase project — no local Docker/mocks. Which project depends on credential precedence, resolved in `loadTestEnv()`: `.env.local` < `.env.test.local` < real environment variables, for `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` / `SUPABASE_SERVICE_ROLE_KEY`.

The middle layer is the one that matters day to day. `.env.local` must keep pointing at production so `npm run dev` shows real data, but the suite creates and deletes ~110 users per run and should not be doing that in the live project. Putting the staging keys in `.env.test.local` (gitignored by the existing `.env*` rule) sends every `npm test` to staging with no flags and no extra command, and leaves the dev server alone; delete the file and tests go back to production. CI has neither file and injects real environment variables, which is why those win outright. `.bulk_cleanup.mjs` deliberately resolves credentials the same way, since a sweep script that follows a different project to the tests is worse than none.

`tests/integration/helpers/testUsers.ts` creates real users via the admin API, signs each in for a real access token, and every test cleans up everything it created (including any group it made a user own — group ownership has no cascading delete, so cleanup order matters) so nothing leaks into the live project. `setupGroup()` (in `tests/integration/helpers/scenarios.ts`) derives each test user's nickname from their `TestUser.tag`, since every test's `create_group`/`join_group` calls route through it — that's the one place a suite-wide nickname requirement gets satisfied. Covers the full privacy/money acceptance checklist: subject invisibility at every market status, parimutuel conservation under randomized/adversarial bet distributions, notification recipient exclusion, balance-capped bet sizing, season rollover. `tests/integration/markets.multiple_choice.test.ts` covers the same checklist for `multiple_choice`: N-option parimutuel conservation, per-option subject invisibility (and visibility at reveal), the union subject cap, hedged bets across options, and the `bets_side_xor_option` constraint rejecting a bet with both/neither of `side`/`option_id` set. `tests/integration/nicknames.test.ts` covers the nickname model itself: join-time collisions, rejoin preserving the existing nickname, and `update_nickname`'s collision/format/non-member checks. `tests/integration/money.payout_distribution.test.ts` covers the `distribute_payout` opt-in: the creator cut (there is no endorser cut, see the money rules above), `bonus_pool` topping up another open market and being absorbed on that market's own resolution, the no-other-open-market fallback holding in `groups.pending_bonus_pool` rather than refunding this market's own bettors, a `bonus_pool`-carrying market voiding with nowhere else to send it (also holds in `pending_bonus_pool`, owner balance untouched), and that pool seeding the next market created (`bonus_pool`/`carried_bonus_pool` both set, pool zeroed). `tests/integration/money.void_by_owner.test.ts` covers the owner kill switch: the non-owner rejection, exact refunds, `market_voided` (never `market_resolved`) and its recipient set, the already-settled rejection, the 404-not-403 for an owner who is the market's subject, and the bonus-pool conservation regression described in the design-decisions note about `refund_all_bets()`. `tests/integration/invite_code_rate_limit.test.ts` covers the invite-code guess limit: ten misses spend the budget, the eleventh is refused (and isn't itself counted, since it never reaches the lookup), the budget is shared with `join_group` so a preview spree closes off joining with a real code, a lapsed window restores normal service, `join_group` returns zero rows rather than raising for a code matching nothing, a code that really exists never counts however often it's used, and the counter table is unreadable by the client it counts. It also pins the minted-code alphabet (2-9, A-Z without I/O) at both call sites that mint one, `create_group` and `regenerate_invite_code` — only ever against codes the suite just created, since older hex codes are still valid and would fail it by design. `tests/integration/markets.clarification.test.ts` covers the resolution-criteria clarification loop: the creator can't request on their own market, subject masking, single-recipient notification to the creator on request vs. broadcast-to-everyone-but-the-creator on update, one update clearing multiple pending requests at once, the no-pending-request rejection, and the `status = 'open'` gate holding even when a request is already pending.

### Continuous integration

`.github/workflows/ci.yml` runs on every pull request, every push to `main`, and on demand (`workflow_dispatch`). Two jobs:

- **`static`** — `npm ci`, `npx tsc --noEmit`, `npx next build`. No database. The build needs the `NEXT_PUBLIC_*` keys because Next prerenders pages that construct a Supabase client at build time, so a missing key fails the build on a page that is fine at runtime.
- **`integration`** — `supabase db push --db-url "$STAGING_SUPABASE_DB_URL" --yes --include-all` against the **staging** project, then `npm test` pointed at that same project, then `node .bulk_cleanup.mjs` as an `if: always()` sweep. Migrations are applied before the tests on purpose: that is what makes a schema change and the tests that exercise it verifiable in the same PR, and it means a broken migration is discovered on staging instead of in a `db push` to production. **`--include-all` matters once more than one migration-adding PR is open at a time**: each PR's CI applies only its own new migrations, so whichever PR's CI runs first lands its migration on staging first, regardless of which filename sorts earlier — without the flag, a second PR whose migration happens to have an earlier timestamp gets refused with "found local migration files to be inserted before the last migration on remote," even though the two migrations have no actual dependency on each other. Safe here because nothing in this codebase's migration history depends on cross-migration ordering within the same PR; a genuinely order-dependent pair still belongs in one migration file.
- **`migrations`** — diffs `supabase/migrations/*.sql` against the PR base (or the previous `main` on a push) with `--diff-filter=AM`, and if the change adds any, upserts a single PR comment saying to run `npx supabase db push` **before** merging. It deletes its own comment if the migrations later leave the branch, so the note can never contradict the diff. On a push to `main` it posts the same reminder to Slack as a backstop. Both messages are rendered by `.github/scripts/migration-nudge.mjs`.

  Why a reminder rather than just running `db push` against production on merge: that would require the production database URL and password as GitHub secrets, and it gets the ordering backwards. It fires the migration and the Vercel build simultaneously and relies on the push winning a race, which is exactly wrong for a destructive migration. Nudging on the PR is the only version that prompts the *correct* action while it is still available, and it keeps every production credential off GitHub. The Slack half cannot know whether you already pushed (checking would need the credentials this design exists to avoid), so it is worded as a reminder, not an alert.

- **`notify`** — `needs: [static, integration, migrations]` with `if: failure()`, posting a Block Kit card to the `#barbets-errors` webhook via `.github/scripts/slack-ci-failure.mjs`. One job rather than a step in each, so a run that breaks in both places produces one message. `failure()` rather than `always()` keeps concurrency-cancelled runs out of the channel, and naming a status function in the `if` is also what stops this job being skipped alongside `integration` on a fork PR. The payload is built in Node from environment variables (never argv or string interpolation) so a quote or newline in a commit message cannot break it, and the step no-ops when `SLACK_ERROR_WEBHOOK_URL` is unset, matching `errorReporter.ts`'s rule that reporting an error must never cause one.

The staging project is a second, ordinary Supabase project. Nothing in the repo references it; it exists entirely as GitHub Actions repository secrets (Settings > Secrets and variables > Actions):

| Secret | Where to get it |
| --- | --- |
| `STAGING_SUPABASE_URL` | staging Project Settings > API, Project URL |
| `STAGING_SUPABASE_ANON_KEY` | same page, `anon` / publishable key |
| `STAGING_SUPABASE_SERVICE_ROLE_KEY` | same page, `service_role` key |
| `STAGING_SUPABASE_DB_URL` | staging Project Settings > Database > Connection string, **Session pooler** (port 5432), password percent-encoded |
| `SLACK_ERROR_WEBHOOK_URL` | the same `#barbets-errors` webhook already in `.env.local`; omit it and the Slack steps no-op |

There is deliberately no VAPID secret: `NEXT_PUBLIC_VAPID_PUBLIC_KEY` is read only inside `usePushSubscription`'s subscribe handler, behind a null check, so it cannot affect a build. And deliberately no *production* credential of any kind, which is the constraint that shapes the `migrations` job below.

Things about the staging project that are deliberate and easy to get wrong:

- **Session pooler, not the direct connection string.** GitHub-hosted runners have no IPv6, and Supabase's direct database host (`db.<ref>.supabase.co`) is IPv6-only, so a direct URL times out on the runner while working from a home machine. The transaction pooler (port 6543) is also wrong here: it cannot hold the session-level state `db push` needs. The password must be percent-encoded because the CLI parses the value as a URI.
- **Raise the auth rate limits.** The suite creates roughly 110 users and signs each one in, all from one runner IP. The hosted default of 30 sign-in/sign-up requests per 5 minutes per IP throttles that into spurious failures. Raise "Sign in / sign ups" (Authentication > Rate Limits) on staging well above the default.
- **Leave `pg_cron` and `pg_net` disabled on staging.** Every test drives the scheduled work by calling `expire_stale()` (and friends) explicitly, so nothing needs the scheduler, and the `cron.schedule` calls in the migrations are already wrapped in `exception when others then raise notice` blocks so they skip cleanly on a project without the extensions. This matters beyond tidiness: `20260707194059_schedule_send_push.sql` hardcodes the *production* Edge Function URL, so a staging project with both extensions enabled would call production's `send-push` every minute.
- **Email confirmation stays off / irrelevant.** Tests create users with `email_confirm: true` through the admin API, so no mail is ever sent.
- **Staging drifts, and that is tolerable.** A migration from an abandoned PR branch stays applied to staging forever. When the drift starts to matter, `npx supabase db reset --db-url "<staging session pooler URL>"` replays every migration onto an empty database, which doubles as the check that the 143-file migration history is still replayable from scratch.
- **Fork pull requests skip the `integration` job** (`if:` guard on the job). Fork PRs cannot read repository secrets, so the job would fail for reasons unrelated to the change.
- **CI runs serialize on the database.** The `integration` job sits in a `barbets-staging-db` concurrency group with `cancel-in-progress: false`, for the same reason `vitest.config.ts` sets `fileParallelism: false`: tests share project-wide state (`expire_stale()` closes *every* eligible market, not just the one under test). While one run holds the group only one other can queue; a third is cancelled by GitHub and needs a re-run.

## Deployment

- **CI**: see "Continuous integration" above. It gates nothing by default — to make a red run actually block a merge, turn on branch protection for `main` and mark the `static` and `integration` checks required.
- **Branching**: work goes on a feature branch and merges to `main` through a PR (as of 2026-08-12; the history before that is all direct-to-main). A direct push to `main` still runs CI, but only after Vercel has begun deploying, so the check arrives too late to prevent anything. The PR is what turns CI into a gate.
- **Migration ordering**: merging deploys app code and *not* migrations, so the two can arrive out of order. For an additive migration (new column, new function, new enum value) run `npx supabase db push` against production **before** merging, so the schema is waiting when Vercel ships the code. Only a destructive migration has to go after the merge, and that one wants a two-step deploy rather than a quick follow-up. CI's `migrations` job comments this on any PR that adds a migration, and reminds you in Slack if you merge one anyway.
- **Source**: [github.com/LukeStro47/barbets](https://github.com/LukeStro47/barbets), `main` branch. The Vercel project is Git-connected, so a push to `main` alone triggers a production deploy — `npx vercel --prod` is no longer the deploy step (still useful for a one-off preview deploy from a dirty working tree).
- **Database**: edit/add a file in `supabase/migrations/`, then `npx supabase db push` (applies directly to the linked hosted project — there's no local Docker instance in this setup). Not tied to the Vercel Git deploy; run it yourself whenever a migration lands. CI pushes migrations to *staging* only, so production migrations stay a deliberate manual step.
- **Edge Function**: `npx supabase functions deploy send-push --no-verify-jwt` after editing `supabase/functions/send-push/index.ts`. Also not deployed automatically by the Vercel Git integration. Its secrets (`VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`/`FCM_SERVICE_ACCOUNT_JSON_B64`) are set via `npx supabase secrets set`, not the Vercel env vars below — this function runs on Supabase's infrastructure, not Vercel's.
- Production env vars (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `NEXT_PUBLIC_VAPID_PUBLIC_KEY`) live in the Vercel project settings, not in `.env.local` — Git-triggered builds run on Vercel's servers and never see the local file.
- Vercel and Supabase CLI logins are both stored on-disk globally on this machine (not tied to any particular terminal/Claude session), so any new session can run these commands without re-authenticating.
- **Native shell**: adding or upgrading a Capacitor plugin needs `npx cap sync` (writes the plugin into both `android/` and `ios/`) *and* a real native build/store release. A Vercel deploy does not carry it, even though the WebView loads the deployed site for everything else — the JS calling the plugin ships instantly, the native half doesn't, so guard any new plugin call behind `Capacitor.isNativePlatform()` and a web fallback. Currently installed: `@capacitor/app`, `@capacitor/camera`, `@capacitor/filesystem`, `@capacitor/share`, `@capacitor/splash-screen`, `@capacitor/status-bar`, `@capacitor-firebase/app`, `@capacitor-firebase/messaging`.
- Useful one-offs: `npx tsc --noEmit` (typecheck), `npx next build` (production build), `npm test` (full suite).

### Domains and the mybarbets.com split

Three hostnames, two Vercel projects:

| Host | Project | Serves |
| --- | --- | --- |
| `app.mybarbets.com` | this repo | the app. Canonical. |
| `barbets.vercel.app` | this repo | Vercel's default alias. Kept working indefinitely, because it is what every native install shipped before versionCode 5 still loads. |
| `mybarbets.com` (+ `www`) | `barbets-www` | the marketing site: landing page, `/how-it-works`, `/download`, `/support`, `/moved`, canonical `/privacy` and `/terms`, and `/go/[batch]`. |

Nothing in this repo resolves an origin at runtime any more. `lib/appOrigin.ts` is the single source for links meant to leave the app, `app/layout.tsx` pins `metadataBase` to it, and `capacitor.config.ts` names it directly. Anything that navigates *within* the app stays a relative path so it keeps working on every hostname and inside the WebView.

**Why the split exists at all:** the Apple Developer account moved from Individual to Organization (MyBarbets LLC dba Barbets), and Apple requires the organization's website to be a real site with substantive content. `mybarbets.com` was pointed at this deployment, so it served `app/page.tsx`, which is a login splash. That is the "minimal content" Apple rejects. `mybarbets.com` also has to keep answering `/go/<batch>` forever, because that URL is printed on physical cards.

**The part that is genuinely hard, and the reason this needed a plan rather than a DNS change:** an installed PWA is welded to the origin it was installed from. `public/manifest.json` sets `id`, `start_url`, and `scope` all to `"/"`, and those resolve against the origin, so an install made from `mybarbets.com` *is* `https://mybarbets.com/` as far as the browser is concerned. There is no API to move one. A redirect does not migrate it, and on iOS a standalone web app that navigates cross-origin gets ejected into Safari. Web push subscriptions are bound to that origin's service worker registration, and the Supabase session is in host-scoped cookies. So everyone who installed from `mybarbets.com` has to re-install and sign in again, full stop. The work is in making that graceful rather than in avoiding it.

What that produced, in the order it has to happen:

1. `components/pwa/MovedBanner.tsx`, mounted in `app/layout.tsx`, renders only when `window.location.hostname` is `mybarbets.com`/`www.mybarbets.com`. That is exact targeting for free: an installed PWA is bound to its origin, so the people who need the message are precisely the ones whose browser is on that host, and this code only runs when the page was served from there. Push cannot be aimed this precisely, because `push_subscriptions` records no origin and the endpoint is an opaque FCM/Mozilla URL. Deliberately *not* worth an `origin` column: it would be carried forever for a one-week problem. Delete the component once the dust settles.
2. The domain moves off this project onto `barbets-www`. Not atomic (one domain, one project), so expect a short 404 window.
3. Supabase **Site URL** changes to `https://app.mybarbets.com`, *after* the move, not before. `getOrigin()` in `lib/actions/auth.ts` builds `resetPasswordForEmail`'s `redirectTo` from the request `Host` header, so reset emails sent before the move carry `mybarbets.com/auth/confirm?token_hash=...` links that are already in people's inboxes and cannot be edited. `barbets-www` forwards `/auth/:path*` (and `/join/:code`, `/login`, `/groups/:path*`, and friends) to `app.mybarbets.com` with the query string intact specifically so those keep working. Keep every existing entry in the Redirect Allow List; they cost nothing.
4. **Still outstanding, and it has to wait for step 2:** delete `app/go/[batch]/route.ts` from this repo and move `APPLE_APP_STORE_URL` to the `barbets-www` project. Deleting it any earlier breaks the printed QR codes, because `mybarbets.com/go/<batch>` still resolves here until the domain actually moves. The `barbets-www` copy is already live and byte-identical on the Android branch.

`app/robots.ts` (disallow everything) is already in place. It is safe ahead of the domain move rather than after it: while `mybarbets.com` still points here it has nothing worth indexing anyway, and the marketing project serves its own permissive `robots.txt` the moment the domain moves across.

**The native shell now points at `app.mybarbets.com` too** (`capacitor.config.ts`'s `server.url` and the `APP_URL` in `public/offline.html`, which is bundled rather than served and so cannot import `lib/appOrigin.ts` or be fixed by a deploy). Both native projects are synced and `versionCode` is bumped to 5 / `versionName` 1.3, so this needs a store release to reach anyone. **It signs out every existing Android user once**: sessions are `@supabase/ssr` cookies, cookies are host-scoped, and a new WebView origin means an empty cookie jar. The FCM token survives, so pushes keep arriving and open a logged-out app. Ship it with something users want and say so in the release notes. Installs that have not updated keep working, because `barbets.vercel.app` still serves this same deployment — which is why that alias stays alive rather than being retired.

## Notable design decisions worth remembering

- **The bonus pool earned a fourth strip cell; the over/under line still doesn't.** This doc previously argued that the strip is exactly three cells everywhere and a `bonus_pool` should be a note underneath. That was wrong for one specific reason: the note existed to explain that the Pool figure *excluded* the bonus (`get_open_bet_volume` sums `bets` and nothing else), so the strip was quietly understating the money on the table and spending a sentence apologizing for it. The fix is arithmetic, not layout — Pool now reads `openBetVolume + bonus_pool`, which is what will actually pay out, and once the figure is honest the sentence has nothing left to say. The Bonus cell is what keeps that total decomposable, and the explainer behind it (`BonusPoolValue`) shows the two numbers adding up. The over/under line is *not* an analogous case and stays in `LineTicket`: it is not money, so it doesn't belong in the money rail, and unlike the bonus it is never folded into a figure that would otherwise lie.
- **A rate limit cannot be counted by a function that raises.** The invite-code limit looked like a five-line change: count the misses, raise when there are too many. It doesn't work, and it fails silently in the direction of "no limit at all" — `RAISE` aborts the transaction, so the `not_found: invalid invite code` that reports the miss also rolls back the row recording it, and the counter sits at zero forever while the guessing continues. There is no autonomous-transaction escape hatch in Postgres to write around it. So the miss path has to *return* rather than raise, which is a real deviation from this codebase's "business-rule errors raise, callers map them" convention and is worth the exception only because the alternative is a limit that doesn't limit anything. Two more traps sit right behind it, both of which the integration suite caught rather than review: PostgREST runs `STABLE` functions in a read-only transaction, so the preview function had to become `VOLATILE` before it could write at all; and a function declared `returns memberships` that returns NULL serializes as a row of all-null columns, not as `null`, so `join_group` had to become `returns setof memberships` and signal a miss with zero rows (`20260813150000`) before any caller could actually detect one. All three failures are invisible from reading the code and only show up when you check whether the counter is going up and whether a bad code is really rejected.
- **The "we moved" interstitial on mybarbets.com has to be client-side, and being client-side is what makes it legitimate.** The marketing site's `/` is also the `start_url` of every PWA installed from that domain before the split, so it has to be two pages at once: a real marketing page for browsers (and for the Apple reviewer whose whole objection was that the domain had no content) and a re-install prompt for stranded home-screen icons. There is no server-side signal for "launched from a home screen" — no header carries it — so the fork cannot happen on the server. It runs as a blocking inline script ahead of all page content, setting a class from `matchMedia('(display-mode: standalone)').matches || navigator.standalone === true` (both checks: the first is the Android/Chrome signal, the second the WebKit one), with two CSS rules hiding one block or the other. A React effect would run after first paint, which on a cold PWA launch over cellular is a visible second of "why is my app gone" before the explanation appears. The important consequence is that the server emits identical bytes to everyone, so Googlebot and Apple see the marketing page because neither is in standalone display-mode — this is the opposite of cloaking, and the marketing half is server-rendered and works with JavaScript off. Deliberately not an automatic redirect: an iOS standalone app that navigates cross-origin is ejected into Safari, so a redirect would dump someone into a browser tab with no explanation, where a button they chose to press is understood. Known gap: iOS 17.4+ in the EU launches home-screen web apps as ordinary Safari tabs, where both signals read false, which is why the marketing header carries a permanent "Open the app" link.
- **The marketing site deliberately serves no web app manifest.** Not an oversight and not just "we don't want people installing a landing page." `public/manifest.json` here uses `id: "/"`, which resolves against the origin, so a manifest served from `mybarbets.com` with the same id would be treated by Chrome as an *update to the WebAPKs already installed from that domain* — and changing `display`/`start_url` on an installed app is under-specified across browsers. That would be gambling with the exact population the migration exists to rescue. Serving none leaves those installs launching to `/` with the manifest they already cached, which lands them on the interstitial, which is the desired outcome.
- **404-not-403 everywhere.** A hidden subject and a genuinely nonexistent market must be indistinguishable, at every layer, forever.
- **Business-rule errors return, they don't throw**, specifically inside Server Actions — see the Server Actions section above. This bit us once already (a bet-timing race showed as a raw "server error" instead of friendly copy) before the whole action layer was converted.
- **Ledger is append-only** with no client mutation policy, as defense in depth on top of RLS already blocking it.
- **A cron sweep over every group needs per-row error isolation, or one bad row takes down the platform.** `expire_stale()` is invoked as `select expire_stale();`, which is one statement and therefore one transaction, and PL/pgSQL cannot commit partway through one. Until `20260813180000` the body had no error handling at all, so a raise anywhere rolled back every group's work in that run — and because nothing committed, the next tick re-selected the same row and died identically. One poisoned row stops market auto-close, auto-finalize, season archiving and group deletion for *everyone*, indefinitely, and says nothing while doing it. The fix is a `begin ... exception ... end` block per loop iteration, which is an implicit savepoint. Four things about that shape are load-bearing: the state change and its `_emit_notification_event` call stay in the **same** block (a rolled-back close must not leave a queued push behind); the failure record survives because it's written in the outer transaction while only the inner savepoint rolled back; recording is an upsert with an attempt counter, since a stuck row is retried every minute and one row per minute would bury its own signal; and bare `when others` is safe here because Postgres deliberately excludes `QUERY_CANCELED` and `ASSERT_FAILURE` from it, so a statement timeout still propagates instead of being swallowed and retried forever. The cost to remember: each block allocates a subtransaction, and past 64 in one transaction Postgres overflows its per-backend cache and slows every concurrent snapshot check — which is why the blocks wrap whole iterations rather than individual statements, and why this wants revisiting if one run ever processes hundreds of rows.
- **A SECURITY DEFINER function that reads `auth.uid()` cannot be called by cron, and the failure is silent.** `expire_stale()` called `end_season()` on every season past its `ends_at` for roughly three weeks without a single one succeeding: `end_season()` derives its caller from `auth.uid()`, which is NULL under pg_cron, so its membership check matched nothing and it raised `not_found`. Timed seasons simply never ended, and the raise took the whole sweep down with it — the two bugs above and below this one are the same incident. The lesson generalizes past this call site: **authorization belongs in a thin wrapper, and the work belongs in an internal function that takes its actor as a parameter.** `_end_season(p_group_id, p_actor_id)` asks no authorization questions and accepts NULL for "nobody did this, a date arrived"; `end_season(p_group_id)` is now just the not_found/forbidden gate in front of it. Worth checking any other function reachable from both a client and the cron path against this. It also stayed invisible because every season test in the suite used `seasonLength: 'manual'`, which leaves `ends_at` NULL and never enters the loop — a reminder that a test fixture's convenient default can define a blind spot exactly the shape of the untested branch.
- **Housekeeping that shares a transaction with load-bearing work inherits its failures.** The `notification_events` retention delete was folded into `expire_stale()` by `20260714100000` on the reasonable grounds that one more cron schedule is one more thing to maintain. `20260813180000` reverses that, for two reasons the original couldn't have known: it made a 30-day cleanup hostage to a market-closing bug, and `notification_events` has no index on `processed_at` (only the partial one on unprocessed rows), so it sequentially scanned the whole table every minute to find, essentially always, nothing. It now runs daily as `purge_processed_notification_events()` — and running daily is precisely what makes the plain scan fine, which is why no index was added for it. Same reasoning as `send_nudges()` being kept separate: don't let the optional share a failure domain with the load-bearing.
- **The push queue claims before it sends, and that is at-most-once on purpose.** The obvious way to raise the old 50-events-per-run ceiling is to raise the number, and that is the one change that makes things worse: `send-push` used to select unprocessed rows and write `processed_at` only after sending, so a run that overran its cron minute had its entire batch selected again by the next tick and every recipient got the push twice. `claim_notification_events()` marks and returns in one statement with `for update skip locked`, which has to land *before* any of the parallelism, not after. The cost is that a run dying mid-batch drops the events it claimed instead of retrying them next minute. That is close to what this pipeline already did (a send that failed for one recipient was logged, never retried) and the blast radius is one missed notification, since nothing in this path moves tokens. The at-least-once version — a separate `claimed_at` column plus a sweep releasing claims left by a dead run — is the right upgrade if a dropped notification ever starts to matter, and is more machinery than today's volume earns.
- **A parameter default is not a limit, and `limit null` is not a small limit.** `claim_notification_events(p_limit int default 200)` looks like it bounds how much of the queue one `send-push` run takes even when the caller says nothing. It doesn't, because PostgREST never uses a function's default: the query it builds passes every argument by name, filled from the request body via `json_to_record`, so a body missing the key passes NULL. And `limit null` in Postgres is the same as no `limit` clause at all, so the "safest" call shape (let it default) was the one that claimed the entire backlog in a single statement. With at-most-once claiming, a run that takes the whole queue and dies partway through sending drops every event it claimed, which is exactly the blast radius the batch size exists to bound. `20260813160000_claim_limit_null_is_not_unlimited.sql` moves the default to where it applies, `limit coalesce(p_limit, 200)`. The general lesson for this codebase: any `default` on a PostgREST-reachable function is documentation, not a guarantee, and if a NULL for that parameter would be dangerous, `coalesce` it in the body.
- **Subject cap is `member_count - 2`**, not `- 3` — the creator and the endorser are the only two roles that strictly can't overlap with the subject set; both can also bet on their own market, so no third "bettor" role needs reserving. For `multiple_choice`, this cap applies to the union of distinct subjects across every option, not per option. Stays `- 2` even for a `require_endorsement = false` group, where a market never actually gets a separate endorser — see the `create_market`/`sponsor_market` bullet above for why that's deliberate, not an oversight.
- **The vote window and challenge window share one owner-configurable duration** (`group_settings.resolution_window_hours`, default 8h, 0.5-10h in half-hour steps), and a vote auto-finalizes early the moment everyone eligible has voted rather than always waiting out the clock.
- **A resolution proposal can beat the clock.** `propose_resolution` accepts a market that's still `open`, not just `closed` — the instant the proposal commits, betting locks for everyone. `closes_at` stays the *latest* possible close; `closed_at` records when it actually happened, so the UI can distinguish "closed early by proposal" from a normal timeout. There's deliberately no reopen mechanism — a premature proposal that turns out to be wrong just gets challenged and voted VOID like any other bad proposal.
- **Leaving a group no longer refunds your open bets** — only being a market's *subject* forces a void+refund on leave/removal. This closes an exploit where a member could peek at closed-market odds, then leave to claw back a stake they knew was going to lose. A self-service leave goes to `left` (rejoinable, balance preserved, never reseeded, nickname freed, invisible everywhere else) — a real state distinct from `dormant` (still fully visible, nickname reserved, used only for a member who joined mid-intermission and hasn't missed anything) and from `removed` (owner-initiated, permanent, invite code rotated). A `left` member who actually bet before leaving is the one deliberate exception to "invisible everywhere": the leaderboard still surfaces their real historical record.
- **Turnout apathy upholds the proposal, it doesn't void.** Before this, a tie or zero-turnout vote always voided the market — which made challenging a free "undo" for a losing bettor betting on the group not bothering to vote. Now the proposal wins a tie it's part of, and wins outright if nobody votes; a tie that excludes the proposal (the group disagreed but couldn't agree on what's true instead) still voids.
- **Multiple choice markets generalize via `option_id`, not a new outcome enum.** Every column that used to hold a `bet_side`/`market_outcome` value grew an `option_id` sibling with a same-table XOR CHECK constraint, so `finalize_market`'s money-critical payout math is one shared code path across all three market types instead of a per-type branch — the one place a bug would be catastrophic stays the one place the logic lives.
- **`ledger.bet_id` is optional for `reason = 'payout'`, unlike `bet`/`refund` which always require it.** Added for the `distribute_payout` creator/endorser cuts, which are market-level rewards with no single bet behind them. `market_id` is optional for `payout` too now, for the one case that isn't even market-level: `_finalize_season()`'s even split of a leftover `groups.pending_bonus_pool` fires at season-archive time, after the season (and everything in it) is already gone. `bet`/`refund` are unchanged — both always require both.
- **`refund_all_bets()` must exclude the market it is refunding from its own bonus split, because "is this market open?" is asked before the status flips.** The original version split a voided market's `bonus_pool` across `status = 'open'` markets in the group with no self-exclusion. That looked safe, and the VOID-resolution path proved it every time in tests: `propose_resolution()` moves the market to `proposed` before `finalize_market()` refunds, so it is already out of the `open` set. But the three callers that force-void directly — `void_market_by_owner()`, `void_market_by_creator()`, and `_void_market()` (zero-bet auto-void at `closes_at`, member removal, the intermission sweep) — all refund *first* and set `status = 'voided'` after, so a still-`open` market handed its bonus back to itself and the unconditional `update markets set bonus_pool = 0` two lines later destroyed it. Tokens left the group's economy entirely: not to another market, not to `pending_bonus_pool`. Fixed in `20260811130000_refund_all_bets_excludes_self_from_bonus_split.sql`. The general lesson is worth more than the fix: a helper that reads a row's status is reading it at *the caller's* moment in its own sequence, not at some canonical one, so any status predicate inside a helper needs to hold for every caller's ordering. The regression test in `money.void_by_owner.test.ts` asserts the group's *total* bonus (every market's `bonus_pool` plus `pending_bonus_pool`) is unchanged across the void rather than asserting a specific destination, so it can't be defeated by another open market happening to exist in the fixture.
- **`bonus_pool` money is redistributed, never re-taxed.** When a zero-winner-pool market's remainder tops up another market's `bonus_pool`, that inherited money rides through untouched by that second market's own `distribute_payout` cut if it also happens to hit its own zero-winner-pool case — only real stakes are ever taxed. This keeps the payout math from decaying every time money hops between markets.
- **Nicknames are per-group, not global.** The old design claimed a single global `username` at signup, gating every other action behind that claim. Real usage showed people wanted to go by different names in different friend groups, so identity moved onto `memberships.nickname` (set on join/create, changeable via `update_nickname`) and the claim step disappeared entirely — a profile row is just auto-created on first sign-in.
- **A group's time zone is a display caption, not an input-interpretation feature.** It tells members what zone the person who set a closing time meant; it does not make `datetime-local` inputs read differently per visitor. Revisit this if real usage shows people actually need the input itself to be zone-aware.
- **Deleting a group voids everything immediately but removes it 5 days later.** This entry used to claim deletion was instant and final; it hasn't been since `20260714121000_group_deletion_grace_period.sql`. `delete_group` voids+refunds every open market in the same call (so nobody's bet/vote is left in limbo) and then sets `groups.deletion_scheduled_at = now() + interval '5 days'` rather than deleting the row — the group stays fully readable for those 5 days so everyone can see how their last markets actually landed, `cancel_group_deletion` can call it off, and `expire_stale()` does the real delete once the timestamp passes. The abandoned-intermission auto-deletion sweep uses the same column and the same 5 days. The client-side gate is still a type-the-group-name confirmation, and the "5 days" figure is quoted in three places in the UI (the delete sheet, `GroupDeletionBanner`, and the how-it-works edge cases tab) — change the interval and all three need changing with it.
- **Awards use two different recompute cadences on purpose.** 7 of the 8 are comparative rankings that only recompute every 3rd market resolution, so a title doesn't flap back and forth on a couple of noisy bets; Risk Taker updates live because it's monotonic (a new holder only ever appears via a genuine new all-time-best payout multiple), so there's nothing to flap in the first place. Don't reflexively make a new title recompute live "for freshness" — check whether it's actually monotonic first.
- **The reveal page is a shareable image, not just a page.** `RevealTicket.tsx` captures itself to a PNG via `html-to-image` the moment it mounts (not lazily on click) — waiting until a share tap would put an `await` between the user's click and `navigator.share()`, and Safari revokes the share sheet's required user-activation across an awaited gap. Any image inside that captured node (the coin logo) has to be a plain `<img>`, never `next/image`, since `html-to-image` needs a same-origin asset with no optimization endpoint in the way.
- **A layout's `redirect()` does not protect the pages under it, and `requireUser()` exists because that assumption reached production.** `app/(app)/layout.tsx` has always done `if (!user) redirect('/login')`, and every page beneath it was written as though that settled the matter, reading `user!.id` directly. In the App Router a layout and its page render **in parallel**: both are already in flight, so the layout's redirect cannot stop the page from executing. Any request whose session had quietly expired threw `TypeError: Cannot read properties of null (reading 'id')` from whichever page ran, which is invisible in development (sessions rarely lapse mid-session) and intermittent in production. `requireUser(supabase)` in `lib/supabase/server.ts` is now the only way any page under `app/(app)` gets the user, layout included, so the rule is checkable: **no `auth.getUser()` call may appear under `app/(app)` at all.** The non-null assertion was the tell throughout; if code needs `user!.id`, it needs `requireUser()` instead. Server Actions were already correct (they return `{ error: 'Not signed in.' }`), and `submitFeedback()` now degrades rather than throwing, since its durable row is saved before the user lookup and a lapsed session should cost the Slack card a name, not the feedback.
- **A reported error's stack must come from `util.inspect(error)`, never `error.stack`.** Next.js sets `Error.prepareStackTrace` to a deliberately *un*-sourcemapped implementation on startup (`next/dist/server/patch-error-inspect.js`) and does its mapping instead through a `Symbol.for('nodejs.util.inspect.custom')` handler on `Error.prototype`. So `error.stack` is minified **by design**, and an explicit `prepareStackTrace` override beats Node's own source-map support, which is why `process.setSourceMapsEnabled(true)` cannot fix it. Reading the error through `util.inspect` triggers Next's handler and yields real files and lines. That is the difference between a Slack card saying `at s (.next/server/chunks/ssr/[root-of-the-server]__1s6o8a3._.js:1:12574)` and one saying `at GroupFeedPage (app/(app)/groups/[groupId]/page.tsx:59:41)`. `lib/errorReporter.node.ts` holds the one `inspect()` call, dynamically imported behind a `NEXT_RUNTIME === 'nodejs'` check because `lib/errorReporter.ts` is reachable from the edge bundle (`instrumentation.ts` is bundled for both runtimes) and a static `node:util` import there breaks that build. Two things that look like they should be part of this and are **not**, both tried against a production build and measured before being removed: `experimental.serverSourceMaps` (Turbopack already emits 236 map files on a stock `next build`, so it changes nothing) and enabling Node's source-map support (inert, per the override above). Neither is needed and neither belongs back in.
- **`pg_policies` is the source of truth for what a policy currently says, not the `create policy` statement in the migration history.** Six policies (`groups_select`, `group_settings_select`, `memberships_select`, `seasons_select`, `season_optins_select`, `season_results_select`) were rewritten in place by `ALTER POLICY` in `20260707131619_phase3_security_fixes.sql` and have not resembled their `create policy` text since. Reconstructing them from that text — the obvious way to write a migration that touches every policy — would have reintroduced the 42P17 infinite recursion that fix existed to kill (`memberships_select` querying `memberships` from inside a policy *on* `memberships`), **and** silently dropped the `status not in ('removed', 'left')` filter `_caller_is_active_group_member()` has grown since, handing a left member their old group back. This was caught by running the candidate migration against the real schema inside a `begin`/`rollback` and diffing per-user visible row counts across every RLS-gated table before and after; that check is worth repeating for any future policy change, and is cheap (`SET LOCAL ROLE authenticated` plus a `request.jwt.claims` setting reproduces exactly what PostgREST does). The general rule: read the catalog first, and prefer `ALTER POLICY` so a rewrite can only restate the expression, never quietly change the command or the role list.
- **A resolved market explains its own arithmetic, behind one "Full ledger" row.** `SettlementLedger.tsx` replaced three separate things under the reveal ticket: a 🎁 card noting that the pool started with carried bonus tokens, a "nobody predicted this one" breakdown card, and an always-expanded list of every bet. Each was a fragment of the same question ("where did the money go?"), and between them they never answered *how* any figure was reached — most conspicuously the dust rule, which is the one thing on the page that looks like a bug if you don't know it: the biggest winning stake is paid one or two tokens more than `floor(stake × pool ÷ winning pool)` gives them. The modal now states the pool's composition, the rule that settled it (one of the three real paths: parimutuel win, full refund, or the no-winner split), where the rounding remainder went and to whom, and then the bets.
  - **It reconstructs the settlement from what `finalize_market()` left behind rather than being told it**, which is what let this ship with no schema change. `markets.bonus_pool` is zeroed the instant a market resolves, so "how much of this pool wasn't staked?" has no column to read — but `sum(payouts) == total_pool + bonus_pool` exactly, by construction, so the bonus is just the payouts minus the stakes. (On the no-winner split path every payout is 0 and `payout_breakdown`'s four keys sum to the same total instead.) The dust holder is likewise found by recomputing each winner's *base* payout and looking for the one who was paid more than the formula alone allows — steadier than re-deriving the biggest-stake / earliest / lowest-id tie-break in TypeScript and hoping it stays in step with the SQL. Nothing here re-implements the payout; the payouts are read.
- **Sharing an image needs a native code path, and a web-only one silently degrades to something worse instead of failing.** `lib/shareImage.ts`'s `useShareableImage()` is the one implementation, used by `RevealTicket` and by `/profile`'s `ShareRecordCard`; both previously carried their own copy and both were broken in the Capacitor WebView, which has **no `navigator.share` and no `navigator.canShare` at all**. Neither reported an error — the ticket's fallback ladder quietly dropped to `navigator.share({url})` and then to copying a *link* (to a page nobody outside the group can even open, in place of the one thing the ticket exists to be), and the record card dropped to an `<a download>` the WebView ignores, so its button looked simply dead. Two smaller traps are fixed in the same place and worth not reintroducing: `html-to-image`'s `toBlob` *resolves to `null`* rather than throwing when the canvas won't export (so a failed capture has to be checked for, not just caught), and revoking a download's object URL on the line after `a.click()` can cancel the save before it starts.
- **`/profile` is scoped to one group at a time, with exactly one deliberate exception: the "Still open" rail.** Every figure on the page (balance, standing, accuracy, net, best call) is a per-group number that would be meaningless aggregated, which is why the `GroupSwitcher` at the top defines the scope of everything under it. Open bets are the exception because they aren't a statistic, they're a list of things you have to come back for, and scoping them meant the page couldn't answer "what have I got riding?" without switching through every group. The rail therefore queries every non-`removed` membership's group, sorted soonest-to-close, and stays honest about it by stamping each card with the group it belongs to (only when the member is in more than one) rather than merging them into an anonymous total — the per-group identity rule is about not inventing cross-group *aggregates*, not about never listing two groups' rows together. This is still not an Inbox: it lists your own open positions, not work items assigned to you (see the BottomNav note below for why that page stayed deleted). It is now also the **only** entry point to your own bets: the group header's "My bets" ticket icon is gone, which leaves `/groups/{id}/bets` routable but unlinked (see "Notable design decisions").
- **Resolution criteria can only change in response to an open clarification request, never as a free edit, and only before betting closes (`open` or `pending_sponsor`).** This closes the obvious exploit (a creator quietly rewording a wobbly market after odds are visible) without blocking legitimate tightening — the creator can always act once *someone* has flagged the ambiguity, and one update satisfies every pending flag at once rather than requiring them to be dismissed one by one. `pending_sponsor` is included because the endorsement gate is *for* catching a bad question, and an endorser who can't ask what a vague criterion means until after they've vouched for it has no way to use that gate for its actual purpose.
- **The market page is one template with a fixed section order, not a per-status layout.** Every in-flight market screen runs the same five slots top to bottom: (1) your position, if you have one; (2) otherwise the card explaining what you're choosing between — the line, or the options; (3) how it settles; (4) what happens next, with that stage's one action folded into it under a divider; (5) the pinned slip. The two things worth knowing about it:
  - **Slots 1 and 2 are mutually exclusive on purpose.** The explainer card disappears the moment you have a position, because the position ticket's header band already carries the same fact ("Over / Under · line 12 min", "One of 4 options"). Two cards restating one thing is what the old layout did.
  - **The stage's action always lives inside slot 4, never where betting lives.** "Propose result early"/"Propose the outcome" and "Challenge this call" are both full-width and never paired with descriptive text — the timeline steps above them are the explanation. Floating either one near the slip makes it compete with betting. They differ in weight, on purpose: proposing is filled in espresso, because on a `closed` market it is the one thing left for anyone to do and an outline made the page look like it had no next step; challenging stays *outlined* in danger, because the expected path through the proposed screen is reading the call and letting the window run out, and a filled button there would ask everyone to treat the exception as the default. Neither is honey — honey (`#e8a33d`) stays reserved for the single committing action on screen: Place bet, Endorse it, the Bet pill. Choice controls are deliberately neutral so the UI never nudges a side.
- **The redesign's live payout projection was dropped rather than built, because it is a live odds readout by another name.** The market template as drawn showed "If it lands → 610 back" on the position card and "you get back N at the current split" in the bet drawer, both while betting is still open. Anyone can divide their way from a payout figure back to the pool split, so shipping it would have quietly repealed the sealed-odds rule (`get_closed_odds` raises `odds are not available until betting closes`, and `create_market`'s whole "you bet on what you believe, not on what everyone else believes" premise rests on it). The position ticket therefore drops its right-hand column entirely while open — `computeStakedPositions()` exists for exactly that case — and the drawer commits to "Balance after," the one number it can state honestly. Both unseal into the full drawn design the moment the market closes. (The stake itself is a real text field with the quick amounts as shortcuts into it, not a display that happens to accept typing: the chips are derived from the group's `seed_amount`, so they can never cover every group, and someone who wants to stake 37 has to be able to just say 37.) **If a payout preview is ever wanted while open, it needs to be a deliberate decision to end sealed odds, not a UI change.**
- **An aggregate the client computes is an aggregate the client has to download first.** Four pages showed one "all-time net" figure and all four got it by selecting every non-seed ledger row and adding them up in JavaScript. None of it was an N+1 and none of it was a loop, which is why it read as fine: the groups hub even had a comment noting it was one query for every group rather than one per card. It was still the whole lifetime ledger crossing the wire to render one number per card, growing for as long as the group was played. `membership_ledger_net` (above) moves the addition into Postgres. Measured on the real database at the time: 745 non-seed ledger rows collapse to 75 view rows, and the heaviest single user's hub went from 125 rows to 3. **A view, not a SECURITY DEFINER function, and that was the whole design decision** — `security_invoker = true` computes the aggregate under the caller's own RLS, so it grants no visibility the client-side sum didn't already have. A function would have been a privacy change wearing a performance costume, and the review would have had to be about privacy instead of about speed.
  - **It surfaced two call sites that were already silently reading nothing.** Because `ledger_select_own` is own-rows-only, any read of *another* member's ledger rows comes back empty, and two places were quietly relying on one. Confirmed against production data rather than inferred from the policy text: a group-mate can see 0 of another member's 31 non-seed rows while seeing all 44 of their own. Neither was a regression from the view, which is why the view reproduces the existing behaviour exactly rather than quietly changing it; they were dealt with separately, and differently:
    - **The leaderboard's "leader is up N this week" trend line is gone.** It read the leader's last seven days of `ledger`, got nothing for any viewer who wasn't the leader, and fell through to confidently telling everyone else "level this week" regardless of what had happened. Removed rather than repaired, because repairing it is not a bug fix: it needs a SECURITY DEFINER function and a deliberate ruling that one member's weekly swing is another member's to see. **The dangerous version is the one that looks like it works**, so the comment where it used to live says not to re-add it by reading `ledger` directly.
    - **The departed-member check got a purpose-built function instead.** Deciding whether someone who left still belongs on the leaderboard ORs a `bets` read with a `ledger` read, and only the `ledger` half was blind (`bets_select` does expose others' bets on resolved markets), so the OR had quietly collapsed to the bets half alone. Two things fell through the gap: the case that half exists for (a departed member with no bets of their own but a real creator/endorser payout cut), and a timing one nobody designed, since `bets_select` only reveals other people's bets on *resolved* markets, so a departed member with bets still riding dropped off the board until those settled. `group_members_who_played()` answers it. **Unlike the trend line, this one was worth the privacy decision because the disclosure is a single bit that the feature already publishes**: if they're on the leaderboard, you can see they played. The function returns membership ids and nothing else, for exactly that reason.
- **The group feed fetches per-market extras in batches, and only its settled half is paged.** The hub's market list was built by looping over every market in the group and querying inside the loop — a bet count for each open market, the odds for each closed one, a proposal row and an option label for each proposed one — with no `limit` on the market query itself. That is one round trip per market, awaited one at a time, on a list that grew for the life of the group, so a year-old group's hub took seconds to render and got worse every week. Three things about the fix are worth keeping:
  - **The rule is "no query inside a per-market loop," not "fetch less."** `lib/groupFeed.ts` collects the ids that need each extra, fetches each extra for all of them in one `.in()`, and builds the cards from Maps with no `await` in the loop at all. The page already did exactly this for reactions and the viewer's own bets; the loop was where the pattern hadn't been applied. `get_open_bet_count` and `get_closed_odds` are the two leftovers, because they only accept a single market id and giving them `uuid[]` siblings is a migration — they are at least fired concurrently now, so the cost is the slowest call rather than the sum. If the active buckets ever get slow, array-valued versions of those two are the next move.
  - **Only settled markets are paged, and that asymmetry is the point.** Open and pending markets are bounded by what a group has going on right now, and hiding one behind a "Load more" would hide something the viewer can still act on. Resolved ones accumulate forever and nobody scrolls to the three-hundredth, so the Settled tab loads 20 and fetches the rest on demand.
  - **The page cursor is `(resolved_at, id)`, and the timestamp is never round-tripped through a JS `Date`.** Offset paging is wrong here because a market resolving mid-read shifts every later row down by one, which shows up as a duplicated or skipped card. `resolved_at` alone is not enough either: a season-end sweep voids every still-open market in one transaction and `now()` is per-transaction, so dozens of rows can share an identical timestamp. And the timestamp has to travel back to Postgres byte-for-byte, because timestamptz keeps microseconds (`...:00.028641+00:00`) while a JS `Date` keeps milliseconds — re-serializing one moves the page boundary and silently drops the rows in between. - **Adding a new trailing default parameter to a Postgres function does not replace an existing overload — and this has bitten this project five separate times.** Four were caught the hard way (most visibly `update_group_settings` picking up a fourth new parameter across three different features); the fifth, `_cleanup_departing_member`, was found only by running the catalog query below and had been sitting in the database undetected for a month (`20260810120000_drop_stale_cleanup_departing_member_overload.sql` removes it). That one is the instructive case, because every symptom that normally exposes this was absent: all three callers passed the new parameter, so nothing errored, and the helper is internal and revoked from `authenticated`, so PostgREST never touched it. What made it worth finding anyway is that the orphaned body was a *stale money rule* — it unconditionally refunded a departing member's open bets, the exact behavior deliberately removed to close the peek-then-leave exploit. **The lesson: "nothing is broken" is not evidence there's no leftover overload. Only the catalog query is.** A function's identity in Postgres is its argument *type* signature, not its defaults — `CREATE OR REPLACE` with a longer signature creates a second overload alongside the old one, and PostgREST then can't pick a candidate for a call that omits the new parameter (and worse, the error only surfaces the next time someone calls it *without* the new param — a function only ever touched with the new signature looks completely fine until then). Every signature change needs an explicit `DROP FUNCTION <old signature>` for the superseded version in the *same migration* that adds the parameter, not a "add first, drop unlisted the moment it breaks" approach. After pushing, verify with a throwaway call passing every parameter by name (`supabase.rpc(name, {...all params...})`) — if PostgREST error-message-dumps two candidate signatures, an overload was left behind. The direct check, which doesn't depend on guessing which call site breaks, is to ask the catalog whether any function name has more than one signature:

```sql
-- Extension-owned functions (citext, pg_net, ...) legitimately overload and would
-- otherwise drown the result, so exclude anything that's an extension member.
select p.proname, count(*), array_agg(pg_get_function_identity_arguments(p.oid))
from pg_proc p
join pg_namespace n on n.oid = p.pronamespace
where n.nspname = 'public'
  and not exists (
    select 1 from pg_depend d
    where d.objid = p.oid and d.classid = 'pg_proc'::regclass and d.deptype = 'e'
  )
group by p.proname having count(*) > 1;
```

Anything this returns is either a deliberate overload (there are none in this project today) or a leftover that will fail the next time someone calls it the old way. As of `20260810162000` this returns zero rows across all 73 app-owned functions, verified after `update_group_settings` **lost** a parameter (`p_endorser_payout_pct`) rather than gaining one — the rule is identical in both directions, since a function's identity is its argument type list either way. Run it after any migration that changes a signature.

To confirm an ambiguity without executing anything (these are money functions, so don't just call them and see): `explain select the_function(...)` **without** `analyze` plans the statement, which resolves the overload, but never runs the body. An ambiguous call fails at plan time with `42725 function ... is not unique`.
- **Hedging is opt-out per group, not a global rule.** `group_settings.allow_hedged_bets` defaults to on (today's parimutuel behavior, unchanged for every existing group) specifically to close a real exploit: betting big on a heavy favorite and a token amount on the underdog manufactures a favorable risk profile regardless of outcome. The enforcement lives in `place_bet` itself; `BetslipBar`'s client-side block (disabling the confirm button when a selection conflicts with an existing bet) is just a courtesy, same relationship every other business rule here has to its UI.
- **`BetslipBar` replaced the old inline `PlaceBetCard`** with a persistent bottom bar, styled like the reveal ticket, that slides up into a confirmation sheet instead of a form sitting mid-page. The point is a bettor always sees a clear stub (side, amount, balance after) before confirming, not a form that just resets silently on submit — a successful bet hands off to a full-screen success view (small checkmark animation, respects `prefers-reduced-motion`) before returning to the refreshed market page. Quick-amount chips are 1%/5%/10% of `group_settings.seed_amount` (the tokens a new member starts with), rounded to the nearest 5, not a percentage of current balance — balance swings with every bet, seed amount doesn't, so it's the stable reference point for "a small/medium/large bet in this group."
- **Tailwind v4's `space-y-*` puts margin on the bottom of every child except the literal last one, not margin-top on all-but-first like v3.** A `position: fixed` element still receives that margin even though it's out of normal flow, and for a `bottom-0` element an unwanted margin-bottom shows up as a real gap between it and the true screen edge. This bit `BetslipBar` for real: it renders a Fragment of four top-level elements (an in-flow spacer, the closed bar, a backdrop, and the sheet) into a `space-y-*` container, and the *sheet* ends up as the container's actual last child, not the bar — so only the bar got the stray margin, which is exactly why it floated while the sheet always sat flush. Confirmed by reproducing both states (24px gap without a fix, 0px with) before shipping the fix: every top-level element `BetslipBar` renders now carries an explicit `!m-0`, rather than relying on which one happens to land last in the DOM.
- **The market page's "Closes in" stat tile signals urgency with a breathing danger-colored border, not honey.** Honey is already this app's one accent color (the "Line" tile for over/under markets, every primary button), so reusing it to also mean "hurry up" would blur two different meanings into one color — `danger` (already used for form errors) reads as "pay attention" without colliding with it. `ClosesInStatTile.tsx` computes the under-1h threshold client-side on the same 30s tick `CountdownTimer` already uses, rather than a value frozen at page load, so it turns on live for anyone watching a market close in real time instead of requiring a refresh. The border (`.animate-urgent-breathe` in `globals.css`) fades to a static `danger-500` outline under `prefers-reduced-motion`, same posture as the bet-confirmed checkmark and `RevealTicket`'s capture guard.
- **A season ending doesn't mean every in-flight market gets discarded, but it also doesn't wait forever.** The old `end_season()` force-voided anything non-terminal the instant it ran, which meant a market someone had already started resolving (proposed, maybe already challenged) got thrown away along with everything else. `winding_down` splits the two cases: nothing-started-yet force-voids immediately (there's nothing to wait on), already-in-flight gets to finish through its normal timers, capped `resolution_window_hours` past season end so a stuck vote can't hold a season open indefinitely. The three call sites that can trigger the actual archive (`end_season`'s synchronous fast path, `finalize_market`'s tail hook, `expire_stale`'s hard-cap sweep) all funnel through one shared `_finalize_season()` helper, same "one place the logic lives" instinct as the multiple-choice payout unification above.
- **`/demo` is a sandbox, not a preview of real data.** A brand-new signed-up user with zero groups has nothing to do until someone joins them, so `app/(app)/groups/page.tsx`'s empty state links to `/demo`: a fully client-side, no-Supabase-calls walkthrough (`components/demo/*`, `lib/demoScenario.ts`) of one fake yes/no market through open → closed odds → proposed → resolved. It always resolves in the visitor's favor so the payout moment lands every time, but the payout itself runs through the real parimutuel formula (`floor(bet.amount * total_pool / winning_pool)`) against a seeded fake pool, so the number is genuinely computed, not scripted. Each step also carries a honey-tinted "explainer" callout (visually distinct from real market content on purpose) teaching *why* that step works the way it does, not just narrating what's on screen. Deliberately doesn't touch `is_market_visible()`, `place_bet`, or any other real function — it's a UI-only teaching tool, not a real market in disguise. First-touch entry into it is `components/groups/OnboardingCarousel.tsx`: a full-screen, swipe-through (CSS scroll-snap, real touch swipe plus dots/Next for non-touch), six-slide, non-interactive explainer shown once (a permanent `localStorage` flag, same one-shot convention `InstallBanner` uses) the first time a member lands on the empty `/groups` hub, ending in a CTA into `/demo`. The "Try a live demo" button on that empty state stays as the re-entry point for anyone who already dismissed the carousel.
- **Navigation moved from a top `AppHeader` to a fixed bottom bar (`components/layout/BottomNav.tsx`), and Inbox was deleted outright rather than re-homed.** Four icon tabs (Home, Markets, Board, You) plus a contextual `+`; Home doesn't navigate, it opens a floating group switcher, and the `+` opens a "New market" type picker in-group or a "New group" teaser outside one. `BottomNav` is deliberately route-derived, not prop-driven: `lib/navRoute.ts`'s pure `getActiveNavTab`/`getRouteGroupId`/`shouldHideBottomNav` read the pathname to figure out the active tab, the current group, and whether to render at all, so none of the ~15 pages under `(app)/` need to thread nav state down manually. It's mounted as a sibling of `PullToRefresh`/`PageTransition` in `app/(app)/layout.tsx`, not nested inside either — both wrap `{children}` in a div that sometimes carries a CSS `transform` (the pull-down offset, the page-slide animation), and any computed transform on an ancestor silently breaks a `position: fixed` descendant's containing block (the same footgun `PageTransition`'s own comment documents for `BetslipBar`). `BottomNavSpacer` (just a conditional `pb-24`, not `fixed`) reserves scroll room for it and *is* safe to nest inside those wrappers. The `+` sheet's betting-off check reuses the exact copy/`Modal` `NewMarketButton` already showed for this case; picking a market type there hands off to `/groups/{id}/markets/new?type=...`, and since the drawer has already asked that question the wizard on the other side has no type picker at all (`initialMarketType` is now the market's type, not a pre-selection; a direct hit on the route with no `?type=` falls back to `yes_no`). Inbox's four "waiting on you" buckets (needs endorsement, awaiting vote, awaiting resolution, needs clarification) weren't re-homed anywhere cross-group when it was deleted — three of the four were always visible per-group already (`GroupFeedPage`'s status buckets), and the clarification one still shows as the market card's "!" badge. **This was in fact missed in practice, and `lib/tasks.ts` brought back the smallest useful piece of it** (see the tasks paragraph above): the two buckets that are genuinely blocked on one specific person, surfaced as a per-group card, a per-row count, and a Home-tab red dot. What deliberately did *not* come back is the Inbox *page* — there's still no cross-group destination that aggregates work items, only counts that point you into the group they belong to.
- **Nudges got their own cron job, not a branch inside `expire_stale()`.** Every sweep in `expire_stale()` is load-bearing: markets closing, votes auto-finalizing, seasons archiving, groups being deleted. The two nudges are flavor. Putting them in the same function would mean a bad query in a marketing prompt could throw partway through and leave a season un-archived, so `send_nudges()` runs as `barbets-nudges` on its own 15-minute schedule with its own failure domain. The corollary is worth stating: **new sweeps default to a new job, and only join `expire_stale()` if they're genuinely part of the state machine.**
- **The two nudges decide "is there anything worth notifying about," never "who."** `send_nudges()` only picks groups and markets; the entire "not a subject, hasn't bet on this market, hasn't bet anywhere in this group for 7 days" rule lives in `get_event_recipients`, alongside every other recipient rule in the app. Splitting it the other way would have created a second place where "who can see this market" is decided, which is exactly the thing `is_market_visible()` exists to prevent.
- **The closing nudge's rate limit is per group, not per recipient.** One nudge per group per 24 hours, checked against `notification_events` itself. Per-recipient would be more precise, but the recipient set for two markets closing in the same group is the same lapsed-member set, so the group-level check gives the same answer and needs no per-user delivery log to maintain and prune.
- **A payout that exactly equals the stake is not a win worth quoting.** It can only happen on a one-sided market (nobody took the other side, so there are no losing stakes to split). The reveal ledger used to render it as "+0 won", which read as a bug, and the push quoted the stake as winnings, which overstated it. Both now say the call was right and the stake comes back. The check is `payout == stake`, not a separate flag, because the parimutuel formula makes those two facts the same fact.
- **Two editable percentages became one editable and one computed.** The universal-loss split used to ask for a creator % *and* an endorser %, which required a "these can't sum past 100" validation, a matching Postgres check constraint, and an error state in two forms. Removing the endorser's cut (it rewarded a one-tap role with no risk attached, and nobody ever tuned the number) left one real decision plus arithmetic, so the remainder is now displayed read-only rather than asked for, and the whole class of invalid input stopped existing. **When a second input is fully determined by the first, show it instead of collecting it.**
- **Group logos are static assets with a free-text key, not a Storage bucket or an enum.** The art is app-authored, identical for every group, and never user-supplied, so there is nothing to gate: `public/avatars/` plus `lib/avatars.ts` gets CDN caching, no bucket, no signed URLs, and no second access-control system (contrast `resolution-proofs`, which really is user-supplied and really does need mediating). `groups.avatar_key` stores plain text with only a shape check so that adding or retiring an avatar is a PNG and one line of TypeScript, with no migration, and a key the current build doesn't recognize quietly falls back to the initials tile instead of erroring.
- **Dropping the "BB-" invite prefix rewrote every existing code rather than grandfathering them.** Two live formats would mean every input, paste handler, and support conversation has to know about both forever. Old links keep working through one normalizer (`lib/inviteCode.ts`) applied at the three entry points every join funnels through, so no Postgres function ever learns that the old format existed, and the tolerance can be deleted in one place once printed cards age out.
- **`season_optins` and `season_optouts` are two separate tables on purpose, not one table with inverted meaning.** The obvious design once seasons flipped to opt-out-by-default would be to rename `season_optins` and read "no row" as "included." That breaks `_cleanup_departing_member()` (shared by `leave_group`/`remove_member`), which already deletes a departing member's opt row on every departure — under an inverted single table, that delete would silently *un-exclude* them instead of excluding them, auto-reseeding someone who explicitly left. Keeping both tables (`season_optins`: a dormant member asking in; `season_optouts`: an active member asking out) means the existing departure cleanup, `join_group`, and `opt_in_season` needed zero changes — `start_season()`'s reseed rule is just a union of the two default populations.
- **Both create flows are wizards whose first question was already asked by the bottom nav's drawer.** `/groups/new` and `/groups/{id}/markets/new` are the two routes `shouldHideBottomNav()` blanks the tab bar for, and they now each own their whole screen: no `PageHeader`, a step bar (back caret, progress pills, `1 of 2` / `ASK`) and one question per step, with the primary action pinned to the bottom by `min-h-[calc(100dvh-4rem)]` plus `mt-auto` rather than a fixed footer. The point isn't the steps, it's that **the drawer's answers are carried forward as context instead of re-asked**: create-group shows the name and token allocation as a dark ticket with an Edit pill (which opens the same two fields inline, so a typo doesn't mean backing out of the flow), and create-market drops its type segmented control entirely because `?type=` already decided it. Step state is local to the client component — no route per step — so back/forward inside a wizard costs nothing and a half-finished market can't be linked to.

  Two mechanics make that work. **Every route into creating a group goes through the drawer**, including the groups hub's own "Start a group" button, which dispatches a `barbets:new-group` window event that `BottomNav` listens for rather than linking to `/groups/new` — an event and not a search param because there's exactly one listener, it owns state nothing else should set directly, and a half-open drawer isn't worth linking to or restoring on back. And because each step is a screenful with a pinned footer, both wizards `window.scrollTo(0, 0)` on every step change: without it the browser restores the previous scroll position and the flow arrives with its own step bar above the fold. The pinning uses `--flow-height` (`globals.css`), which is `100dvh` minus the layout's in-flow `env(safe-area-inset-top)` padding — sized against a plain `100dvh` the page overflows the viewport by exactly that inset, which is what made these screens scroll a notch even when everything fitted. It's a custom property rather than a Tailwind arbitrary value because `calc(100dvh - env(safe-area-inset-top))` can't safely be written as one: the hyphens inside the `env()` keyword are indistinguishable from the subtraction operator to an arbitrary-value parser.

  Fitting the viewport had a second-order consequence worth remembering: **`PullToRefresh` arms on "scrolled to the very top," and a screen that never scrolls is at the top permanently**, so every downward drag anywhere on the form pulled the refresh indicator. Both wizards therefore opt out via the same `isCreateFlow()` predicate that hides the bottom bar — appropriate anyway, since a wizard's answers live in client state and its only server data is the group and member list it was handed on entry, so there is nothing a refresh could fetch. (`router.refresh()` would in fact have preserved the in-progress answers — it merges an updated RSC payload without discarding unaffected client state — so this is about a gesture that fires constantly and achieves nothing, not about losing work.)
- **Create-group's advanced settings are a separate view with a label-only entry row.** The row says "Advanced settings" and nothing else: listing endorsement/hedging/payout/challenge-window under it would make a first-time group owner feel they had four decisions to make, when the honest answer is that the defaults suit a small group and everything stays editable from Settings. The view itself deliberately uses **the same names and the same copy as the group's own Settings page** — "Hedging", "Split universal losses", Creator % editable with Open markets % shown read-only beside it — rather than friendlier one-off labels, because these are the same four settings seen twice within a few minutes, and a member who renamed them in their head at creation would have to re-learn them the first time they opened Settings. There's no "reset to defaults": the view opens on the defaults, so the button only ever undoes deliberate work.
- **A season name is collected at create time but named afterwards, through `nameActiveSeason()`.** `create_group()` brings the first season into existence, so the name has nowhere to go until it returns. Rather than widen the function's signature (and the migration, and the `DROP FUNCTION` dance that a changed signature requires), `lib/actions/seasons.ts` gained a thin action that looks up the group's `active` season and falls through to the existing `rename_season()` RPC. It's fired best-effort alongside `updateGroupSettings()`/`setGroupAvatar()` after the group already exists, so a failure leaves a group named "Season 1" rather than no group at all.
- **Both horizontal rails need `scroll-pl-5` to match their `px-5`, and it isn't optional.** The "Still open" rail on `/profile` and the awards shelf both break the page gutter (`-mx-5 … px-5`) so cards can bleed to the screen edge while still starting flush with the heading above them. With `scroll-snap-type: x mandatory`, though, the browser snaps on first layout: `scroll-snap-align: start` aligns a card to the scrollport's *border* edge, so it immediately scrolls the 20px of padding away and parks every card 20px left of the text it sits under. `scroll-padding-left` is what tells snapping where the content actually starts. The cards are also sized `calc((100% - 10px) / 2)` rather than a fixed pixel width so exactly two fit a phone screen — which is why the awards rail's dot indicator measures its first child instead of dividing by a hard-coded step.
- **The market subject picker became a chip strip, and "Nobody" became a real chip.** A typeahead is the right control for a list you can't hold in your head; a group small enough to bet in is small enough to show every member at once, and "who is this about?" is a question you answer by recognising a name, not recalling one. Making "Nobody" a selectable chip rather than the absence of a selection is the load-bearing half: it separates "I decided this isn't about anyone" from "I haven't got to that field yet," which the empty typeahead couldn't distinguish. The subject cap (`totalMemberCount - 2`) is enforced by disabling the unselected chips rather than by a message. Chips are alphabetical (membership order is an order nobody can predict) and paged at 20, with **anyone already selected pinned into view regardless of which page they fall on** — paging away someone's own choice reads as having lost it, which is the failure mode any "show more" list has to design against.

They're now single-purpose screens: a header row (back caret + coin), a 34px headline, and one honey CTA. `Card` is retained for surfaces that really do sit among other content (the sign-up terms consent, the invite's group card, the offline balances box), which is the distinction worth keeping — **a card earns its border by having neighbours.**

  Two supporting pieces came out of it. `components/ui/Field.tsx` is the underlined text field that replaced the boxed `inputClasses` string previously copy-pasted verbatim into `AuthForms`, `ForgotPasswordForm` and `JoinFlow`; its label sits above the input but *after* it in the DOM (`flex-col-reverse`) purely so focus styling is a `peer-focus:` variant rather than a client component holding an `isFocused` boolean. - **The splash's "I have an invite code" button routes through the existing sign-in bounce rather than previewing the group pre-auth.** `/join` (no code) is a code-entry screen that does no lookup of its own: it pushes to `/join/[code]`, which already redirects a signed-out visitor to `/login?next=/join/XXXX` and lands them back on the invite once they have an account. The header had two icon chips fighting for the same corner, and the one that mattered (settings for an owner, group info for everyone else) was losing — it's now a single 44px control. Your own open positions are already answered better by `/profile`'s "Still open" rail, which spans every group rather than just this one.
